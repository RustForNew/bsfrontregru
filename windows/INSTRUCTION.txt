XHTTP Setup @@VERSION@@ — быстрый запуск
=========================================

СТАТУС ВЕРСИИ
-------------

Эта инструкция относится только к точной версии в заголовке и именах файлов.
Не смешивайте launcher, PYZ, checksum и инструкцию разных версий. Получайте все
файлы из одного доверенного Release либо одной проверенной сборки/передачи.

WINDOWS: СКАЧАТЬ, РАСПАКОВАТЬ, ЗАПУСТИТЬ
----------------------------------------

1. Нужна Windows 10 версии 2004 (build 19041)+ или Windows 11 и один уже
   установленный WSL2-дистрибутив Ubuntu/Debian.

   Если WSL2 ещё нет, один раз откройте PowerShell от имени администратора:

     wsl --install -d Ubuntu

   Выполните предложенную перезагрузку и один раз откройте Ubuntu. Это системная
   подготовка Windows; сам ZIP не может безопасно выполнить её без прав
   администратора и возможной перезагрузки.

2. Получите xhttp-setup-@@VERSION@@-windows-wsl.zip и его `.sha256` из одного
   доверенного Release либо одной проверенной сборки/передачи. Не подменяйте их
   архивом или инструкцией другой версии.
3. В Проводнике: правая кнопка по ZIP -> «Извлечь все». Не запускайте файлы
   прямо из открытого архива.
4. В извлечённой папке дважды нажмите START-WINDOWS.cmd.

Launcher сам проверит SHA-256 внутренних файлов, выберет WSL2 и при
необходимости установит в Ubuntu/Debian Python и системные утилиты. Папка
_internal служебная: ничего в ней не запускайте, не переносите и не удаляйте.


ЧТО ПОДГОТОВИТЬ
---------------

Выходной VPS:

  - Debian 12+ или Ubuntu 22.04+ с systemd;
  - публичный IPv4 и прямой root SSH по паролю;
  - свободный TCP/8083;
  - без Docker/containerd, Remnawave/чужого Xray, custom nftables/iptables,
    отдельного активного nftables.service и нестандартного UFW.

Сайт REG.RU:

  - сайт уже вручную создан в ISPmanager; мастер сайт не создаёт;
  - «Источник IP-адреса» = «Указать вручную»;
  - в `IP-адрес` выбран bundle хостинга, содержащий нужный IPv4; если рядом
    показан IPv6, в мастер копируется только IPv4 до запятой;
  - E-Mail администратора — реальный контролируемый адрес;
  - псевдонимы пусты, кодировка «не указывать», index.php/index.html оставлены;
  - в карточке именно этого сайта включён PHP -> FastCGI (Apache);
  - «Защищённое соединение (SSL)» включено, порт 443, выбран сертификат
    точного frontend-домена;
  - HSTS и «Перенаправлять HTTP-запросы в HTTPS» выключены;
  - «Редирект домена» = «Редирект не включён», SSI выключен;
  - «Журнал запросов» выключен, «Журнал ошибок» включён; период ротации
    «ежедневно», хранить архивов 10;
  - «Настроить сжатие» и «Настроить кеширование» выключены; список расширений
    для кеширования оставлен штатным;
  - автоподдомены, CGI, тестовый WordPress-домен и Python выключены;
  - `php.ini для домена` оставлен в штатном состоянии формы;
  - ровно одна DNS A-запись, CDN/proxy выключен; DNS A и введённый IPv4
    подключения проверяются как разные роли;
  - AAAA и CNAME для этого имени отсутствуют;
  - основной аккаунт REG.RU имеет SFTP-доступ к document root сайта.

На тарифе/узле должны быть разрешены Apache mod_rewrite, mod_proxy,
mod_proxy_http и флаг [P] в пользовательском .htaccess. FastCGI (Apache)
позволяет запросу дойти до Apache, но сам по себе не подтверждает reverse proxy.
CGI, Python и ProxyRequests включать нельзя: они не исправляют отсутствие [P],
а ProxyRequests On может открыть опасный forward proxy.

IPv6 в bundle vhost не равен DNS AAAA: это разные настройки. Мастер требует,
чтобы для точного frontend-имени DNS AAAA отсутствовала.

Это подтверждённый рабочий baseline, а не утверждение, что каждый переключатель
по отдельности обязателен для всех тарифов. После сохранения снова откройте
карточку сайта и убедитесь, что значения не сбросились. HSTS, redirect,
кеширование и сжатие оставьте выключенными как минимум до первого успешного
E2E. Их последующее включение не проверено этим baseline и требует нового E2E.
Если нужного поля нет в вашей версии панели, не считайте настройку автоматически
эквивалентной: сначала уточните это у поддержки/в документации тарифа.

Необязательный мост, если прямой setup-доступ к REG.RU с ПК не работает:

  - отдельный доверенный Linux-сервер с публичным IPv4;
  - SSH по паролю на фиксированном TCP/22;
  - введённый login после входа имеет UID 0, обычно это root;
  - sshd разрешает TCP forwarding к REG.RU.

Главную страницу готовить или заменять не нужно. Мастер не трогает index.html,
не создаёт заглушку, не копирует и не проксирует RuFox или другой сайт.


ЧТО СПРОСИТ МАСТЕР
------------------

Вводите по одному значению:

  1. IPv4 выходного сервера
  2. SSH port выхода [22]
  3. SSH login выхода [root]
  4. SSH password выхода                  (ввод скрыт)
  5. Использовать мост для входа? [y/N]

Пустой Enter или `n/no/нет` означает прямой доступ с этого ПК/WSL. Если нужен
мост, введите `y`, `yes` или `да`. Мастер сразу дополнительно спросит:

  - IPv4 моста
  - SSH login моста [root]
  - SSH password моста                    (ввод скрыт)

Порт моста не спрашивается: всегда используется TCP/22. Затем в обоих режимах:

  6. точный HTTPS-адрес панели REG.RU,
     например https://vip123.hosting.reg.ru:1500/
  7. основной логин REG.RU
  8. пароль панели REG.RU                 (ввод скрыт)
 9. IPv4 подключения REG.RU из поля «IP-адрес сервера»
10. домен frontend

После «да» три вопроса про мост обязаны появиться до адреса панели. Если их нет,
остановите окно: мост не выбран либо запущена другая/старая распакованная копия.
Не продолжайте прямой доступ, если он вам не подходит. После проверки ключа и
UID 0 мастер обязан напечатать `SSH-мост готов; frontend control-plane направлен
через него`; только это сообщение подтверждает, что ISPmanager/SFTP/TLS будут
направлены через мост.

Пароль панели сначала проверяется как SFTP-пароль основного аккаунта. Только
если SFTP вернул именно отказ аутентификации, появится отдельный скрытый вопрос
про SFTP-пароль; всего допускается не более трёх попыток. Сетевая ошибка или
неверный document root не считаются поводом перебирать пароли. FTP-пароль из
письма заранее не вводится. Если отдельный prompt всё же появился, используйте
password из раздела «Доступ к FTP» основного аккаунта REG.RU. MySQL
login/password/host этому мастеру не нужны.

Мастер не входит в SFTP заново для каждой файловой команды. Он использует один
закреплённый SSH-сеанс на проверку document root, отдельный сеанс для
`302`-контроля `.htaccess`, по одному на каждую из трёх `[P]`-проб и один на
финальную транзакцию. Пробы выполняются последовательно;
между SFTP-входами идёт сетевое измерение, а скрытого быстрого цикла login нет.
Сомнительная файловая команда автоматически не повторяется. Если SSH-сеанс умер
именно во время rollback, допускается один новый закреплённый сеанс только для
сверки журнала и восстановления. Конфликт чужих изменений либо недоказанный
откат — это STOP, а не повод продолжать настройку.

Прямые SSH-команды к exit тоже не выполняют новый password-login для каждой
проверки. Мастер открывает ограниченные закреплённые сеансы отдельно для
проверки доступа, подготовки и применения exit. Дочерняя команда не может
переподключиться напрямую или снова запросить пароль при потере master. После
изменений UFW мастер всё равно делает обязательный новый независимый root-вход;
предыдущий сеанс до результата остаётся доступен для безопасного rollback.
Оборвавшаяся команда автоматически не повторяется.

Document root вручную не вводится. Некоторые ISPmanager возвращают полный
filesystem-путь, другие — путь от корня основного SFTP-аккаунта. Мастер сначала
read-only проверяет путь буквально. Только при точном ответе «каталог не найден»
он однократно сопоставляет тот же путь со стартовым SFTP-каталогом, проверяет
фактический `pwd` и запрещает выход за каталог пользователя. Он не подставляет
конкретный логин/домен и не перебирает произвольные каталоги.

Не нужны: SHA/fingerprint, TLS pin, egress-IP, UUID, XHTTP path, probe port,
команды UFW, firewall-plan, APPLY PC, ручная настройка SSH-туннеля или ручное
редактирование .htaccess. Эти значения и действия мастер получает/выполняет
сам.


ЧТО ИДЁТ ЧЕРЕЗ МОСТ
--------------------

При ответе Y мастер принимает SSH-ключ моста по TOFU, открывает один setup-сеанс
и проверяет UID 0. Через этот сеанс направляются HTTPS ISPmanager, SFTP вместе с
keyscan, TLS/SNI frontend, HTTPS-запросы временной пробы и финальный E2E.

SSH к выходному VPS всегда идёт напрямую с ПК/WSL. DNS A/AAAA проверяется
локально и через мост не направляется. Мост — только временный control-plane:
на него не устанавливается Xray, его адрес не попадает в client.vless/VLESS URI,
и после настройки он не участвует в трафике клиента. Сеанс закрывается при
успехе или ошибке.

Текущий мост дополнительно проверен реальным setup-запуском до ISPmanager,
SFTP и TLS/SNI. На проверенном узле дальнейшая reverse-proxy проба остановилась
до Xray/E2E: поддержка [P] тарифом/узлом не была подтверждена. Поэтому успешного
полного live E2E текущей версии через мост пока нет.


ЧТО ПРОИСХОДИТ АВТОМАТИЧЕСКИ
----------------------------

До изменений на exit мастер read-only проверяет существующий сайт через
ISPmanager, DNS, SFTP и TLS/SNI. ISPmanager используется только для входа и
точного чтения существующей записи сайта: сайт через API не создаётся и не
редактируется. Затем мастер:

  - закрепляет первые host keys exit, необязательного моста и SFTP по TOFU;
    при повторном запуске использует проверенную локальную запись без лишнего
    ssh-keyscan, а реальное SSH/SFTP-соединение строго сверяет ключ;
  - проверяет публичный CA либо автоматически закрепляет стабильный точный leaf,
    не прошедший CA+hostname проверку (обычно self-signed); allowInsecure не
    используется;
  - ставит разрешённые пакеты на чистый exit, безопасно готовит UFW и проверяет
    новый root SSH-вход;
  - измеряет исходящие IPv4 exit и Apache REG.RU;
  - создаёт UUID и случайный XHTTP path;
  - разрешает backend TCP/8083 только от измеренного REG.RU IPv4 /32 и
    запрещает остальным;
  - транзакционно добавляет только свой блок .htaccess, сохраняя чужие правила;
  - выполняет настоящий E2E через локальный SOCKS и сверяет внешний IP выхода.

client.vless и VLESS-ссылка появляются только после успешного E2E. До этого
профиль не считается готовым.

При свежей подготовке active UFW допустим только с точным SSH guard текущего
порта, созданным этим сценарием. При доказанном resume допустимы этот guard и
полная точная пара backend allow/deny из сохранённого состояния. Пустой active
UFW, чужое/дополнительное правило, дубликат, частичная пара или guard другого
порта означают STOP. Временный systemd guard при аварии только отключает UFW и
никогда не удаляет SSH allow; спящее правило после успешного disable сверяется
и убирается следующим запуском.

Для pristine/inactive UFW штатный `(None)` означает пустой inventory. No-END
`user.rules`/`user6.rules` принимаются только при полном совпадении с
проверенным `dpkg` package template, а rewritten-файлы — только как полные штатные
пустые UFW 0.36.x layouts. Лишняя строка в любой части файла даёт STOP.
В фиксированных человекочитаемых labels/headers команд допустимы только
различия регистра, пробелов и пунктуации; пути, rules, keys, identifiers и comments
остаются exact.
Штатные `nft` ownership notices принимаются только для точного полного набора
уже проверенных `ip filter`/`ip6 filter` tables. Неизвестный, смешанный,
неполный или дублированный warning даёт STOP. После неудачного первого enable
официальный empty rewrite/inert UFW scaffold считается восстановлением только
после повторной строгой проверки; сообщение показывает фактическое состояние
rollback guard.

Не запускайте второй мастер и не меняйте UFW/nftables/iptables параллельно.
Автоматический режим предназначен для чистого VPS. Если раньше вручную менялись
raw-файлы UFW `before/after` или внутренние `ufw-*` chains, одного похожего имени
chain недостаточно для доказательства безопасности — используйте ручной аудит
либо новый чистый VPS.


ВАЖНЫЙ КОМПРОМИСС TOFU
----------------------

Ручная подготовка fingerprint больше не нужна. При первом подключении мастер
получает ключи SSH exit, необязательного моста и SFTP frontend через ssh-keyscan
и атомарно закрепляет каждый для точного endpoint. При повторном запуске он
проверяет сохранённую приватную запись без нового ssh-keyscan, затем немедленно
открывает реальное соединение с StrictHostKeyChecking=yes. Исчезновение или
смена ключа останавливает процесс до аутентификации и удалённых изменений.

Шифрование и защита от незаметной подмены после первого контакта сохраняются.
Но независимой проверки личности сервера при самом первом контакте нет:
активная MITM-атака в этот момент может закрепить чужой ключ. Доверие своему ПК
не устраняет сетевой риск. Для обычной установки это осознанный TOFU-компромисс;
при более строгой модели угроз используйте ручной advanced workflow и
fingerprint от независимого канала провайдера.

Для leaf, не прошедшего публичную CA+hostname проверку, мастер требует одинаковый
DER в двух соединениях и сохраняет его SHA-256. В pin-режиме срок, CA и hostname
уже не проверяются, а pin сам по себе не доказывает правильность Apache vhost.
Смена leaf будет заблокирована. Переход на сертификат публичного CA допускается
только после обычной проверки trust store и hostname; публичный сертификат
может штатно обновляться.


ЕСЛИ SFTP SSH-ТРАНСПОРТ НЕ УСТАНОВИЛСЯ
--------------------------------------

Это сетевой/маршрутный сбой, а не доказанный неверный пароль. При выбранном
мосте OpenSSH может закончить сообщение строкой `Connection to UNKNOWN port
65535 timed out`. Число 65535 здесь — служебный placeholder stdio ProxyCommand;
фактическая логическая цель остаётся hostname панели/SFTP на TCP/22. Не
открывайте TCP/65535, не меняйте SFTP-host на IP из письма и не удаляйте
сохранённый TOFU-state.

  1. Закройте завершившееся окно и убедитесь, что второй мастер не запущен.
  2. Выдержите cooldown, указанный хостингом. Если он неизвестен, 15–30 минут —
     осторожная эвристика, а не гарантия провайдера.
  3. Один раз снова запустите ту же свежую распакованную копию и введите те же
     данные. Мастер сам проверит чистую фазу и сохранённые ключи.
  4. Если тот же timeout повторился, больше не запускайте мастер циклом.
     Проверьте у хостинга SFTP на точном hostname:22, блокировку/rate limit и,
     при мосте, исходящий TCP/22 с публичного IP моста.

Только точный `Permission denied` означает отказ credential и разрешает
ограниченный повтор скрытого пароля. Host-key mismatch — отдельный STOP: ключ
нужно независимо сверить у провайдера, а не удалять cache для обхода проверки.


ЕСЛИ ПРЯМОЙ SSH К EXIT ОБОРВАЛСЯ
--------------------------------

`SSH-транспорт оборвался` или `rc=255` не равны доказанному неверному паролю.
Мастер не replay оборвавшуюся команду и сохраняет безопасную recovery-фазу.
Закройте завершившееся окно, убедитесь, что второй экземпляр не запущен, и
выполните не более одного повторного запуска той же свежей сборки после
проверки доступности SSH у VPS-провайдера. Если ошибка повторилась на том же
месте, STOP: проверьте sshd, cloud firewall/ACL, лимиты новых SSH-соединений и
консоль VPS. Не удаляйте pinned key и не ослабляйте StrictHostKeyChecking.

`exact_recovery=failed`, `exact_reconciliation=required` после неудачной
recovery-сессии или `rollback неполон` — немедленный STOP. Не запускайте мастер
ещё раз, пока вручную не сверены phase marker, exact managed UFW comments и
указанный временный каталог. Обычный один retry разрешён только после сообщения
`exact_recovery=succeeded` либо когда программа доказала отсутствие мутации.


ЕСЛИ ЗАПУСК ПРЕРВАЛСЯ
---------------------

Запустите START-WINDOWS.cmd ещё раз и введите те же данные. Мастер проверит
managed exit и продолжит с теми же UUID/XHTTP path. Пароли в recovery state не
сохраняются. Не удаляйте созданный каталог состояния и не запускайте два окна
одновременно.

Если жёсткое прерывание произошло во время временного или финального изменения
.htaccess, автоматическое продолжение остановится fail-closed. Не удаляйте
backups: сначала сопоставьте их с текущим .htaccess по сообщению диагностики.
Если frontend/E2E не завершён, exit уже может быть защищён UFW, но client.vless
не выдаётся.


ЕСЛИ FRONTEND-ПРОБА ВЕРНУЛА ТОЛЬКО 404 И НОЛЬ SYN
-------------------------------------------------

Это не доказательство блокировки probe-порта внешним firewall VPS. Если
контрольное правило с тем же точным XHTTP path и локальным redirect 302
срабатывает, это сильный контроль обработки нужного namespace в
Apache/.htaccess. Серия 404 при правиле [P] и отсутствие SYN на exit означает,
что reverse proxy этого узла/тарифа не подтверждён: [P]/mod_proxy_http может
быть недоступен или отфильтрован политикой провайдера.

  1. Не открывайте диапазон портов и не повторяйте мастер циклом.
  2. Не включайте CGI, Python или ProxyRequests On.
  3. Передайте поддержке безопасную диагностику: точный HTTP status histogram,
     факт срабатывания локального 302 и нулевой SYN capture — без URL с
     секретным path, паролей, UUID и клиентской ссылки.
  4. Запросите явное подтверждение mod_proxy, mod_proxy_http и
     `RewriteRule ... [P,L]` в пользовательском .htaccess именно вашего тарифа.
  5. Продолжайте только на поддержанном узле либо после отдельного adapter;
     FastCGI (Apache) одного недостаточно.

Если вместо 404 показан transport timeout/connection error и ноль SYN, тогда
проверяйте маршрут и внешний firewall по следующему разделу. Ответы 5xx требуют
проверки error log Apache и возможностей proxy у хостинга, а не включения CGI.


ВНЕШНИЙ FIREWALL VPS
--------------------

UFW внутри exit мастер настраивает сам. Отдельный cloud firewall/security group
в панели VPS по SSH недоступен. Обычная установка не требует открывать диапазон
портов. Мастер напечатает три точных случайных высоких TCP-порта. Если внешний
firewall не пропустил probe:

  1. В панели VPS временно разрешите входящий TCP ровно на все три напечатанных
     порта. Не открывайте диапазон 20000-59999.
  2. Снова запустите START-WINDOWS.cmd и введите те же данные. Тройка хранится
     в защищённом state до успешного измерения и будет использована повторно.
  3. После подтверждения IPv4 Apache REG.RU мастер остановится на checkpoint и
     будет ждать Enter. Закройте все три временных порта.
  4. Разрешите во внешнем firewall TCP/8083 только от напечатанного IPv4 /32.
  5. Вернитесь в окно мастера и нажмите Enter; тот же запуск продолжится.

SSH-порт управления должен оставаться доступен. Без API конкретного
VPS-провайдера этот внешний слой нельзя автоматизировать универсально. Если
отдельного cloud firewall нет, ничего вручную открывать не нужно.

Минимальный PC-мастер предназначен именно для REG.RU ISPmanager с endpoint вида
`vipNNN.hosting.reg.ru:1500`. Другой shared-hosting не является drop-in заменой:
даже при разрешённом трафике для него нужен отдельный adapter/advanced workflow.


LINUX
-----

На Debian 12+/Ubuntu 22.04+ установите Python 3.10+, ca-certificates, curl,
coreutils и openssh-client. Скачайте в одну папку xhttp-setup-@@VERSION@@.pyz и
xhttp-setup-@@VERSION@@.pyz.sha256, затем выполните:

  (
    set -Eeuo pipefail
    HASH="$(tr -d '\r\n' < xhttp-setup-@@VERSION@@.pyz.sha256)"
    test "${#HASH}" -eq 64
    printf '%s  xhttp-setup-@@VERSION@@.pyz\n' "$HASH" | sha256sum -c -
    python3 xhttp-setup-@@VERSION@@.pyz --version
    exec python3 xhttp-setup-@@VERSION@@.pyz pc
  )


ПРАВИЛА ХОСТИНГА
----------------

Справка REG.RU перечисляет proxy-сервисы среди запрещённого контента на
виртуальном хостинге. Рабочая техническая настройка не является разрешением и
не гарантирует отсутствие блокировки. Используйте схему только после
письменного разрешения REG.RU либо у провайдера, который явно разрешает такой
трафик:

  https://help.reg.ru/support/hosting/zakaz-hostinga-rabota-s-uslugoy/sovety-po-vyboru-tarifa-hostinga

Мастер не обходит антифрод, лимиты или блокировки, не ротирует домены и не
маскирует трафик под сторонний сайт.

Старый ручной runbook v0.4.x с bridge/fingerprint/TLS_PIN и APPLY PC — только
legacy/advanced-материал. Его вопросы и команды не являются шагами этого
PC-мастера.
