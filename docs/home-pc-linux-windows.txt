XHTTP Setup 0.6.0: автоматическая установка с домашнего ПК
==========================================================

Это подробная справка режима `pc`. Для обычного запуска на Windows достаточно
короткого файла INSTRUCTION.txt из Release и двойного клика по
START-WINDOWS.cmd.

Публичный Release пока остаётся `v0.5.0` и содержит прямой PC-сценарий без
вопроса про мост. Этот документ описывает текущий исходный код `0.6.0`, где
добавлен необязательный setup-мост. Публичного артефакта `v0.6.0` пока нет;
ветка моста подтверждена только локальными/mocked-тестами, а не отдельным
live-развёртыванием.

Текущий workflow не требует ручной подготовки SHA/fingerprint, TLS pin,
EXIT_EGRESS_IP, FRONT_EGRESS_IP, UUID, XHTTP path, probe port, UFW-команд,
firewall-plan или подтверждения APPLY PC. Эти шаги мастер выполняет сам.


1. Граница автоматизации
========================

Уже должны существовать:

  - чистый зарубежный Debian 12+/Ubuntu 22.04+ VPS с root SSH;
  - вручную созданный сайт в ISPmanager REG.RU;
  - DNS A-запись и рабочий TLS-vhost сайта.

Для необязательного режима с мостом дополнительно нужен доверенный Linux-узел
с публичным IPv4, password SSH на фиксированном TCP/22, разрешённым TCP
forwarding и входом пользователя с UID 0 (обычно `root`).

Мастер не создаёт сайт и домен, не меняет DNS-провайдера и не управляет внешним
cloud firewall VPS. Подготовка существующего сайта описана в
docs/reg-ru-ispmanager-setup.txt.

Мастер не меняет содержимое главной страницы. index.html остаётся byte-for-byte
таким, каким был до запуска. Никакая копия, заглушка или reverse proxy RuFox и
другого стороннего сайта не создаётся.


2. Windows
==========

Поддерживается Windows 10 2004 (build 19041)+ и Windows 11 с WSL2.

Если WSL2 ещё не установлен, один раз откройте PowerShell от администратора:

  wsl --install -d Ubuntu

Перезагрузитесь, если Windows этого потребует, и один раз откройте Ubuntu. После
этого:

  1) скачайте опубликованный xhttp-setup-0.5.0-windows-wsl.zip;
  2) в Проводнике выберите «Извлечь все»;
  3) дважды нажмите START-WINDOWS.cmd.

Windows launcher проверяет SHA-256 встроенного .pyz и WSL runner, выбирает
установленный Ubuntu/Debian WSL2 и автоматически проверяет/ставит необходимые
Linux-пакеты. Запуск из открытого ZIP не поддерживается.

Сам launcher не устанавливает системный компонент WSL2: для этого нужны права
администратора и иногда перезагрузка. Если WSL2-дистрибутива нет, он завершится
с точной ошибкой до запроса серверных данных.

Опубликованный Windows ZIP `v0.5.0` всегда использует прямой доступ к REG.RU.
Необязательный мост относится к текущему исходному коду `0.6.0`; не скачивайте
и не подменяйте отдельные файлы под видом несуществующего Release `v0.6.0`.


3. Linux
========

Контроллер: Debian 12+/Ubuntu 22.04+, Python 3.10+, ca-certificates, curl,
coreutils и openssh-client. Скачайте .pyz и соответствующий .pyz.sha256 одного
Release, проверьте checksum и запустите:

  python3 xhttp-setup-0.5.0.pyz pc

При запуске из исходников:

  python3 -m xhttp_setup pc

Пароли вводятся только через TTY. Не передавайте их в argv, environment, shell
history или текстовые файлы.


4. Ровно какие данные вводятся
==============================

Прямой запуск текущего исходного кода задаёт восемь видимых и два скрытых
вопроса:

  1) IPv4 выходного сервера
  2) SSH port выхода [22]
  3) SSH login выхода [root]
  4) SSH password выхода                         скрытый
  5) Использовать мост для входа? [y/N]
  6) точный HTTPS URL панели REG.RU/ISPmanager
  7) основной логин REG.RU
  8) пароль панели REG.RU                        скрытый
  9) IPv4 подключения REG.RU из поля «IP-адрес сервера»
 10) домен frontend

Пустой Enter или N в вопросе 5 оставляет прямое подключение. Ответ Y добавляет
ещё три запроса сразу после пароля exit:

  - IPv4 моста
  - SSH login моста [root]
  - SSH password моста                           скрытый

Порт моста отдельно не вводится: PC-мастер всегда использует TCP/22.

Пример URL панели:

  https://vip123.hosting.reg.ru:1500/

Данные спрашиваются по одному; многострочные credential blocks не нужны.

Если SSH-пароль exit или пароль панели действительно отклонён как credential,
мастер разрешает ограниченное повторение скрытого ввода. Сетевой timeout,
ошибка DNS, неверный document root и любой другой сбой не маскируются под
«неверный пароль».

Пароль панели сначала проверяется для SFTP основного аккаунта. Отдельный
SFTP-пароль спрашивается только после точного SFTP authentication failure. Он
также вводится скрыто и не сохраняется. Общий предел — три попытки
SFTP-аутентификации: пароль панели и до двух вводов отдельного пароля.


5. Необязательный setup-мост
============================

Мост выбирается только ответом на `Использовать мост для входа? [y/N]`. При N
все frontend-подключения выполняются напрямую с Linux/WSL-контроллера. При Y
мастер:

  1) принимает первый SSH host key моста по TOFU;
  2) входит по скрытому паролю на фиксированный TCP/22;
  3) требует, чтобы `id -u` вернул `0`;
  4) открывает локальные loopback-forward только на время setup.

Через мост проходят:

  - HTTPS-вход и read-only lookup существующего сайта в ISPmanager;
  - SFTP `ssh-keyscan`, вход и транзакции `.htaccess`;
  - TLS/SNI-проверка frontend;
  - HTTPS-запросы временной egress-пробы;
  - frontend-плечо финального E2E.

DNS A/AAAA всё равно разрешается локально. SSH к exit, его установка, UFW и
проверка egress выполняются напрямую с контроллера, не через мост. Мост не
получает Xray-сервис, не записывается в итоговый профиль и не участвует в
маршруте клиента после настройки; SSH-сеанс закрывается при успехе или ошибке.

Мост — доверенный привилегированный сетевой посредник на время setup. TOFU
устраняет ручной SHA, но не доказывает первый ключ независимым каналом. Эта
ветка реализации проверена локальными и mocked-тестами; реальное сквозное
развёртывание через отдельный bridge пока не подтверждено.


6. Порядок безопасного выполнения
==================================

До первой мутации exit мастер выполняет read-only проверки. При выбранном мосте
пункты ISPmanager, SFTP и TLS идут через него, а DNS остаётся локальным:

  1) TOFU SSH exit и успешный прямой root login;
  2) read-only вход в ISPmanager и единственное точное совпадение уже
     существующего сайта; create/edit через ISPmanager API не выполняются;
  3) DNS: ровно одна A-запись и отсутствие AAAA; DNS A и введённый
     client-connect IPv4 сохраняются и проверяются независимо;
  4) TOFU SFTP и доступ основного аккаунта к фактическому document root;
  5) TLS/SNI на введённом IPv4.

Только после этого чистый exit проверяется и подготавливается. Мастер:

  - отклоняет Docker/containerd, чужой Xray, custom nftables/iptables,
    standalone nftables.service и неоднозначный UFW;
  - ставит только allowlisted packages;
  - если UFW pristine/inactive, сначала разрешает SSH, включает systemd rollback
    guard, включает UFW и проверяет новую SSH-сессию;
  - измеряет стабильный публичный egress IPv4 самого exit;
  - выбирает свободный стабильный для endpoint probe port 20000-59999 и
    печатает его;
  - транзакционно добавляет временный managed route в .htaccess, собирает SYN на
    exit и требует один стабильный публичный Apache egress IPv4;
  - полностью возвращает .htaccess после пробы;
  - создаёт UUID и случайный XHTTP path;
  - устанавливает закреплённый Xray v26.3.27 как отдельный непривилегированный
    systemd-сервис на TCP/8083;
  - применяет UFW allow от измеренного frontend /32 и следующий deny backend;
  - транзакционно применяет финальный managed-блок .htaccess;
  - запускает временный Xray-клиент, делает запрос через его SOCKS и сверяет
    фактический внешний IPv4 с ожидаемым egress exit.

Только после всего списка создаётся файл client.vless с mode 0600 и печатается
ссылка. Ошибка на любом предыдущем шаге не выдаёт непроверенный профиль.


7. TLS
======

Пользователь не выбирает TLS mode и не вводит SHA-256.

Если сертификат проходит обычную системную CA+hostname проверку, мастер
использует public TLS policy. Плановая ротация сертификата публичного CA не
привязана к прежнему leaf.

Если обычная проверка отклоняет сертификат, мастер выполняет две независимые
TLS-сессии с тем же SNI. Только одинаковый стабильный leaf (обычно self-signed)
может быть автоматически принят и закреплён по SHA-256 полного DER. В pin-режиме
срок, CA и hostname уже не проверяются, а pin сам по себе не доказывает mapping
Apache vhost. Смена leaf блокируется. Переход на публичный сертификат
допускается только после обычной CA+hostname проверки. `allowInsecure` не
используется.


8. TOFU SSH/SFTP/bridge
=======================

Первый поддерживаемый host key exit SSH, необязательного моста и SFTP сохраняется
для точного host:port.
Добавление сервером другого поддерживаемого типа ключа не ломает уже
закреплённый ключ, но исчезновение или изменение сохранённого ключа блокирует
соединение. `UpdateHostKeys` отключён.

Что TOFU даёт:

  - шифрованное соединение;
  - обнаружение подмены на последующих подключениях;
  - отсутствие ручного вычисления SHA-256.

Чего TOFU не даёт:

  - независимого подтверждения личности сервера при первом подключении.

Если злоумышленник проводит активную MITM-атаку именно при первом запуске,
может быть закреплён его ключ. Доверие домашнему компьютеру не подтверждает
удалённый endpoint. Для строгой модели угроз используйте архивный ручной
advanced workflow и получите fingerprint через независимую консоль/поддержку
провайдера.


9. Внешний cloud firewall
=========================

UFW внутри Linux настраивается автоматически. Firewall/security group в панели
VPS не доступен по обычному SSH и различается у провайдеров.

Не открывайте весь диапазон. Если firewall заблокировал probe, мастер напечатает
точный стабильный высокий TCP-порт; временно разрешите только его и повторите
запуск с теми же данными.

После измерения мастер напечатает egress IPv4 Apache. Закройте временный probe-
порт, разрешите внешний TCP/8083 только от этого `/32` и повторите запуск. UFW
внутри VPS мастер настраивает сам; SSH-порт управления должен оставаться
доступен. Полностью автоматизировать provider firewall можно только через API
конкретного провайдера; универсального безопасного API нет.

Если отдельного provider firewall нет, дополнительных действий не требуется:
локальный UFW делает всё сам.


10. Recovery state
==================

Состояние конкретного домена находится внутри WSL/Linux:

  ~/.local/state/xhttp-setup/pc/<domain>/

Каталог закрыт mode 0700, чувствительные файлы — 0600. Пароли туда не
записываются.

Фазы означают:

  preparing                 идут проверки/подготовка
  front_probe_in_progress   временный .htaccess может требовать сверки
  exit_applying             remote exit transaction могла прерваться
  exit_ready                exit подтверждён, frontend/E2E ещё не готов
  front_in_progress         финальный frontend apply/rollback мог прерваться
  complete                  E2E завершён, профиль выдан

После обычного сбоя снова запустите мастер с теми же данными. Для
exit_applying/exit_ready он требует либо строгий local+remote receipt, либо
точный pending intent и повторяет idempotent exit apply с теми же UUID/path.
Состояние Xray, listener, systemd, hashes, UFW и egress сверяется, а не
принимается на веру.

Если front probe/apply завершился ошибкой и rollback подтверждён, фаза снова
становится безопасной для повтора. При жёстком завершении либо неполном rollback
маркер остаётся `front_*_in_progress`, и следующий запуск останавливается до
ручной сверки backups с текущим .htaccess. Это защита от потери параллельной
правки владельца сайта.

Не удаляйте recovery state, чтобы «пройти дальше»: там находятся сведения,
нужные для безопасного продолжения. Не запускайте два мастера для одного домена
одновременно.


11. Карта типичных ошибок
=========================

«Сайт не найден» или «несколько сайтов»
  Проверьте, что домен уже создан в этой ISPmanager и совпадает точно. Мастер не
  создаёт и не выбирает сайт по догадке.

DNS A/AAAA не прошли
  Оставьте одну A-запись, удалите AAAA/CNAME и выключите CDN/proxy. Дождитесь
  распространения DNS. Не подменяйте введённый client-connect IPv4 значением
  DNS по догадке: это независимые роли.

TLS/SNI не прошёл
  Исправьте SSL-vhost сайта на 443. Нестабильный leaf не закрепляется. Стабильный
  leaf неправильного default-vhost может пройти exact-pin этап, но не пройдёт
  последующую route/egress/E2E-проверку нужного сайта.

SFTP login прошёл, но document root недоступен
  Проверьте права основного аккаунта и фактический root сайта в ISPmanager.
  Повторный пароль здесь не поможет.

SSH-мост не вернул UID 0 или не открыл forward
  Нужен доверенный Linux-login с фактическим UID 0 на TCP/22 и разрешённым SSH
  TCP forwarding. Порт моста и ProxyCommand вручную не настраиваются.

TCP/8083 занят
  Exit не является чистым либо там есть чужой сервис. Мастер не уничтожает его.

Обнаружены Docker/custom firewall/foreign UFW rules
  Используйте чистый VPS. Автоматическое слияние firewall разных владельцев
  намеренно не выполняется.

Frontend egress probe не увидел соединения
  Проверьте FastCGI (Apache), разрешение `[P]`, TLS-vhost и внешний cloud
  firewall VPS. Не угадывайте egress-IP.

Исходящий IPv4 REG.RU изменился
  Старый UFW /32 не переписывается автоматически. Нужна осознанная проверка
  нового адреса и восстановление managed state.

client.vless отсутствует
  Это ожидаемо до успешного E2E. Не создавайте ссылку вручную из промежуточных
  файлов.


12. Ограничения хостинга
========================

REG.RU перечисляет proxy-сервисы среди запрещённого контента виртуального
хостинга. Используйте схему только после письменного разрешения REG.RU либо у
провайдера, который явно разрешает такой трафик:

  https://help.reg.ru/support/hosting/zakaz-hostinga-rabota-s-uslugoy/sovety-po-vyboru-tarifa-hostinga

Мастер не обходит запреты, лимиты и антифрод, не ротирует домены и не маскирует
трафик под RuFox или другой сайт.


13. Ручные режимы
=================

Команды exit/front/full/doctor относятся к advanced эксплуатации. Они могут
требовать fingerprint, handoff, firewall acknowledgement и точную строку
подтверждения. Это не шаги режима pc.

Старый пошаговый runbook docs/reg-ru-pinned-tls.txt сохранён только как
legacy/advanced-материал v0.4.x. Его bridge, fingerprint, TLS_PIN и APPLY PC не
являются вопросами текущего PC-мастера и не должны смешиваться с ним.
