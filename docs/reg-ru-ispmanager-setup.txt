REG.RU/ISPmanager: подготовить существующий сайт для XHTTP Setup 0.6.0
=====================================================================

Этот файл описывает только ручное создание сайта — единственный frontend-шаг,
который режим `pc` намеренно не автоматизирует. После подготовки не вычисляйте
SHA/fingerprint, TLS pin, egress-IP и не редактируйте .htaccess: мастер сделает
это сам. ISPmanager используется только для HTTPS-входа и read-only поиска
единственного существующего сайта; PC-мастер не создаёт и не редактирует сайт
через API панели. Выбор необязательного SSH-моста этого ограничения не меняет.


1. Сначала проверить правила провайдера
=======================================

Справка REG.RU перечисляет proxy-сервисы среди запрещённого контента на
виртуальном хостинге. Создание технически рабочей конфигурации не является
разрешением и не гарантирует отсутствие блокировки. Получите письменное
разрешение REG.RU либо используйте хостинг, где такой трафик явно разрешён:

  https://help.reg.ru/support/hosting/zakaz-hostinga-rabota-s-uslugoy/sovety-po-vyboru-tarifa-hostinga

XHTTP Setup не обходит антифрод/лимиты, не ротирует домены и не маскирует трафик
под сторонний сайт.


2. Создать сайт вручную
=======================

Откройте ISPmanager -> «Сайты» -> «Добавить сайт». Названия полей зависят от
версии панели и тарифа, поэтому мастер не отправляет универсальный API-запрос на
создание/изменение vhost.

Для нового отдельного домена задайте:

  - точное имя frontend-домена;
  - назначение IP автоматически либо IPv4, который панель выделила сайту;
  - индексы по обычным настройкам сайта;
  - PHP: FastCGI (Apache);
  - SSL/TLS на порту 443 для этого сайта;
  - HSTS: выключен на время первичной настройки;
  - HTTP -> HTTPS redirect: выключен на время первичной настройки;
  - CDN/proxy провайдера: выключен.

Почему нужен FastCGI (Apache): в проверенной конфигурации REG.RU при выключенном
PHP nginx отвечал 404 до Apache. В результате неизвестный XHTTP path не доходил
до `.htaccess`. Версия PHP для самого proxy-маршрута несущественна; важен режим
передачи запроса Apache.

На frontend должны быть доступны Apache `mod_rewrite`, `mod_proxy`,
`mod_proxy_http` и флаг `[P]` в `.htaccess`. Это возможность тарифа/узла
хостинга, а не пакет, который пользователь может поставить в shared account.

Создайте сайт и откройте его карточку. Запишите:

  - IPv4 подключения сайта — поле «IP-адрес сервера»/назначенный IPv4;
  - точный HTTPS URL панели, включая hostname и порт 1500;
  - основной логин аккаунта;
  - домен.

Если прямой setup-доступ к REG.RU с ПК не работает и будет выбран мост,
дополнительно подготовьте IPv4 доверенного Linux-моста, login с UID 0
(`[root]`) и SSH-пароль. PC-мастер использует для него фиксированный TCP/22.

Точный document root вручную вводить в мастер не нужно: режим `pc` получает его
read-only из единственного точного совпадения сайта в ISPmanager. Если панель
возвращает ноль или несколько совпадений, мастер останавливается.


3. Настроить TLS-vhost
======================

Порт 443 должен предъявлять сертификат именно созданного сайта при его SNI.
Поддерживаются два варианта:

  - сертификат публичного CA, валидный для домена;
  - стабильный leaf для explicit pin (обычно self-signed ISPmanager).

Пользователь не снимает TLS pin. Мастер сначала выполняет обычную проверку
CA+hostname. При любом certificate-verification отказе он получает leaf в двух
TLS-сессиях, требует одинаковый DER и сохраняет exact SHA-256. В этом pin-режиме
срок, CA и hostname уже не проверяются; pin сам по себе не аутентифицирует
mapping Apache vhost. Нестабильный leaf отклоняется, а неправильный vhost не
пройдёт последующий route/egress/E2E. `allowInsecure` никогда не используется.

После будущей замены закреплённого leaf сохранённый pin перестанет совпадать — это
ожидаемая fail-closed остановка, а не повод включать `allowInsecure`. Публичный
CA-сертификат может штатно обновляться при сохранении валидной цепочки и
hostname.


4. Настроить DNS
================

Для точного frontend-имени оставьте:

  Type:       A
  Content:    IPv4 подключения сайта из ISPmanager
  CDN/proxy:  выключен, только DNS

Требуется ровно одна A-запись. Для этого же имени удалите AAAA и CNAME. Мастер
проверяет DNS A и введённый client-connect IPv4 независимо: он не выводит один
адрес из другого и не требует их равенства. DNS lookup всегда выполняется
локально на ПК/WSL, даже если frontend-доступ направлен через мост.

Не вводите вместо этого адрес FTP/SFTP-узла или IP exit. В схеме есть разные
адреса:

  - IPv4 подключения клиента к сайту;
  - hostname SFTP, получаемый из URL панели;
  - зарубежный IPv4 exit;
  - исходящий IPv4 Apache REG.RU, который мастер измерит автоматически.


5. Проверить учётную запись и SFTP
==================================

Режим `pc` принимает:

  - точный URL панели вида https://vipNNN.hosting.reg.ru:1500/;
  - основной логин REG.RU;
  - пароль панели.

Из hostname панели мастер выводит SFTP host, использует порт 22 и основной
логин. Поле «IP-адрес сервера» не является SFTP hostname. FTP- и MySQL-данные не
нужны.

Сначала пароль панели проверяется как SFTP-пароль основного аккаунта. Только при
точном SSH/SFTP authentication failure мастер скрыто спросит отдельный
SFTP-пароль. Если credential принят, но document root недоступен, нужен разбор
прав аккаунта, а не перебор паролей. Всего допускается не более трёх попыток
SFTP-аутентификации: пароль панели и до двух вводов отдельного пароля.

Первый SFTP host key принимается автоматически по TOFU и сохраняется для
hostname:22. При его последующем исчезновении/изменении установка блокируется.
TOFU не подтверждает личность узла через независимый канал при самом первом
контакте; для строгой модели угроз используйте ручной advanced runbook.


6. Прямой доступ или необязательный мост
========================================

После скрытого SSH password exit текущий PC-мастер спрашивает точно:

  Использовать мост для входа? [y/N]

Пустой Enter/N означает прямой доступ к REG.RU. При Y дополнительно вводятся
IPv4 моста, SSH login `[root]` и скрытый password; порт не спрашивается и равен
22. Мастер принимает ключ моста по TOFU и требует успешный вход с UID 0.

Через мост во время setup идут HTTPS ISPmanager, SFTP/keyscan, TLS/SNI
frontend, HTTPS-запросы временной пробы и финальный E2E. SSH к exit остаётся
прямым, DNS проверяется локально. Мост не входит в Xray/datapath или клиентскую
ссылку и закрывается после setup. На нём ничего не устанавливается.

Эта optional-ветка текущего исходного кода подтверждена локальными/mocked-
тестами, но отдельного live-развёртывания через реальный мост пока нет.


7. Что мастер изменит на сайте
==============================

Во время измерения Apache egress мастер временно добавляет только свой
маркированный блок `.htaccess`, делает несколько независимых запросов и
возвращает исходные bytes. Финальный apply так же транзакционно добавляет только
managed-блок XHTTP proxy.

Существующие строки `.htaccess` сохраняются. Перед переключением мастер повторно
сверяет исходный файл и не перезаписывает конкурентную чужую правку. При ошибке
E2E выполняется rollback; при неполном rollback дальнейший автоматический запуск
блокируется до ручной сверки backups.

`index.html`, `index.php` и остальное содержимое сайта не меняются. Режим
`placeholder_mode=keep` не создаёт нейтральную страницу, копию RuFox или
reverse proxy главной страницы.


8. Готовность перед START-WINDOWS.cmd
=====================================

  [ ] Получено разрешение хостинга на такой трафик.
  [ ] Сайт вручную создан в ISPmanager.
  [ ] PHP -> FastCGI (Apache) включён.
  [ ] TLS-vhost точного домена работает на 443.
  [ ] HSTS и HTTP -> HTTPS redirect выключены на время настройки.
  [ ] Для домена есть ровно одна A-запись; client-connect IPv4 известен отдельно.
  [ ] CDN/proxy выключен; AAAA и CNAME отсутствуют.
  [ ] Известны URL панели, основной логин/пароль, IPv4 подключения и домен.
  [ ] Основной аккаунт имеет SFTP-доступ к document root.
  [ ] Если нужен мост: известны его IPv4, UID-0 login/password; TCP/22 и
      forwarding доступны.

После этого запускайте START-WINDOWS.cmd. Не выполняйте разделы ручного
v0.4.x-runbook про bridge, TLS_PIN, FRONT_EGRESS_IP, fingerprints, UFW и
APPLY PC: это legacy/advanced-процедура, а не вопросы PC-мастера.
