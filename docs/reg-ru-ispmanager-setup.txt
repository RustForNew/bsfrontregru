REG.RU/ISPmanager: подготовить существующий сайт для XHTTP Setup 0.6.1
=====================================================================

Этот файл описывает только ручное создание сайта — единственный frontend-шаг,
который режим `pc` намеренно не автоматизирует. После подготовки не вычисляйте
SHA/fingerprint, TLS pin, egress-IP и не редактируйте .htaccess: мастер сделает
это сам. ISPmanager используется только для HTTPS-входа и read-only поиска
единственного существующего сайта; PC-мастер не создаёт и не редактирует сайт
через API панели. Выбор необязательного SSH-моста этого ограничения не меняет.

Документ относится к текущему исходному коду/release-candidate `0.6.1`.
Публичный Release `v0.6.0` — предыдущая версия без новых scoped SSH/SFTP,
strict-UFW и recovery fixes; его поведение нельзя считать эквивалентным этому
документу.


1. Сначала проверить правила провайдера
=======================================

Справка REG.RU перечисляет proxy-сервисы среди запрещённого контента на
виртуальном хостинге. Создание технически рабочей конфигурации не является
разрешением и не гарантирует отсутствие блокировки. Получите письменное
разрешение REG.RU либо используйте хостинг, где такой трафик явно разрешён:

  https://help.reg.ru/support/hosting/zakaz-hostinga-rabota-s-uslugoy/sovety-po-vyboru-tarifa-hostinga

XHTTP Setup не обходит антифрод/лимиты, не ротирует домены и не маскирует трафик
под сторонний сайт.

Минимальный режим `pc` технически привязан к REG.RU: он принимает ISPmanager
URL только вида `https://vipNNN.hosting.reg.ru:1500/` и ожидает соответствующий
API/SFTP contract. Фраза «используйте хостинг, где разрешено» означает выбрать
поддерживаемый вариант или разработать отдельный adapter/advanced workflow;
произвольный другой хостинг нельзя подставить в этот мастер без доработки.


2. Создать сайт вручную
=======================

Откройте ISPmanager -> «Сайты» -> «Добавить сайт». Названия полей зависят от
версии панели и тарифа, поэтому мастер не отправляет универсальный API-запрос на
создание/изменение vhost.

Для нового отдельного домена задайте подтверждённый рабочий baseline:

  Поле/переключатель ISPmanager       Значение
  ----------------------------------  ----------------------------------------
  Имя                                 точный frontend-домен
  Псевдонимы                          пусто, если они отдельно не нужны
  Источник IP-адреса                  «Указать вручную»
  IP-адрес                            bundle хостинга с нужным IPv4
  E-Mail администратора               реальный контролируемый адрес
  Кодировка                           «Не указывать»
  Индексная страница                  штатные index.php index.html
  PHP                                 включён
  Режим работы PHP                    FastCGI (Apache)
  Защищённое соединение (SSL)         включено
  SSL-порт                            443
  SSL-сертификат                      сертификат точного frontend-домена
  HSTS                                выключен
  Перенаправлять HTTP в HTTPS         выключено
  Редирект домена                     «Редирект не включён»
  SSI                                 выключено
  Журнал запросов/access log          выключен
  Журнал ошибок/error log             включён
  Период ротации error log            ежедневно
  Хранить архивов                     10 (штатное значение формы)
  Настроить сжатие                    выключено
  Настроить кеширование               выключено
  Расширения для кеширования          оставить штатный список (кеш выключен)
  Автоподдомены                       отключено
  CGI-скрипты                         выключено
  Тестовый домен для WordPress        выключено
  Python                              выключено
  php.ini для домена                  оставить штатное значение панели
  CDN/proxy провайдера                выключен

В актуальной форме REG.RU пункт `IP-адрес` может показывать одной строкой
bundle `IPv4, IPv6`. Выберите bundle, чей **IPv4 до запятой** совпадает с IPv4
подключения из письма/карточки хостинга. В PC-мастер вводится только этот IPv4,
не вся строка и не IPv6. Наличие IPv6 в dropdown vhost не создаёт DNS AAAA:
это отдельная DNS-запись, которая для frontend-имени должна отсутствовать.
E-Mail администратора нужен панели, но мастер его не читает.

Версию PHP выбирайте из поддерживаемых тарифом: для самого proxy-маршрута важен
режим FastCGI (Apache), а не конкретный номер версии. После сохранения снова
откройте карточку сайта и проверьте, что панель сохранила все значения и
сертификат. Если в вашей версии панели отдельного переключателя нет, это не
доказывает эквивалентность проверенному baseline — уточните поведение тарифа.

HSTS, HTTP -> HTTPS redirect, кеширование и сжатие оставьте выключенными как
минимум до первого успешного E2E. Их включение после этого не входит в
проверенный baseline: меняйте по одному и каждый раз повторяйте полный E2E.
Live-сценарий подтверждает комбинацию целиком, но не доказывает причинность или
необходимость каждого из четырёх последних переключателей по отдельности.

Если `php.ini для домена` в вашей форме уже включён, оставьте его включённым;
мастер не читает и не меняет этот флаг. При выключенном кешировании список
расширений ниже не активен — не очищайте его. Значения ротации относятся только
к включённому error log и не участвуют в XHTTP route.

Почему нужен FastCGI (Apache): в проверенной конфигурации REG.RU при выключенном
PHP nginx отвечал 404 до Apache. В результате неизвестный XHTTP path не доходил
до `.htaccess`. Версия PHP для самого proxy-маршрута несущественна; важен режим
передачи запроса Apache.

На frontend должны быть доступны Apache `mod_rewrite`, `mod_proxy`,
`mod_proxy_http` и флаг `[P]` в `.htaccess`. Это возможность тарифа/узла
хостинга, а не пакет, который пользователь может поставить в shared account.
`FastCGI (Apache)` подтверждает только передачу неизвестного URL в Apache; он не
подтверждает reverse proxy. До установки получите у поддержки явный ответ про
`RewriteRule ... [P,L]` в пользовательском `.htaccess` именно на вашем тарифе.
Не включайте CGI, Python или `ProxyRequests On`: они не добавляют нужный reverse
proxy, а `ProxyRequests On` может открыть опасный forward proxy.

Создайте сайт, сохраните его, снова откройте карточку и запишите:

  - IPv4 подключения сайта — IPv4 до запятой из выбранного bundle/поля
    «IP-адрес сервера»; не копируйте соседний IPv6;
  - точный HTTPS URL панели, включая hostname и порт 1500;
  - основной логин аккаунта;
  - домен.

Если прямой setup-доступ к REG.RU с ПК не работает и будет выбран мост,
дополнительно подготовьте IPv4 доверенного Linux-моста, login с UID 0
(`[root]`) и SSH-пароль. PC-мастер использует для него фиксированный TCP/22.

Точный document root вручную вводить в мастер не нужно: режим `pc` получает
API-путь read-only из единственного точного совпадения сайта в ISPmanager. Если
панель возвращает ноль или несколько совпадений, мастер останавливается.

На разных ISPmanager API-путь может быть полным filesystem-путём либо путём от
корня основного SFTP-аккаунта. Мастер не угадывает путь по логину/домену: сначала
проверяет API-значение буквально. Только при однозначном `No such file` он
строит единственную вторую трактовку от фактического стартового SFTP `pwd`,
снова выполняет read-only `cd; pwd` и принимает только безопасный результат в
каталоге пользователя. Ошибка прав, смешанная диагностика, неоднозначный `pwd`
или выход за стартовый каталог останавливают установку до мутации exit.


3. Настроить TLS-vhost
======================

Порт 443 должен предъявлять сертификат именно созданного сайта при его SNI.
Поддерживаются два варианта:

  - сертификат публичного CA, валидный для домена;
  - стабильный leaf для explicit pin (обычно self-signed ISPmanager).

Пользователь не снимает TLS pin. Мастер сначала выполняет обычную проверку
CA+hostname. При любом certificate-verification отказе он получает leaf в двух
TLS-сессиях, требует одинаковый DER и сохраняет exact SHA-256. В этом pin-режиме
срок, CA и hostname уже не проверяются; pin сам по себе не аутентифицирует
mapping Apache vhost. Нестабильный leaf отклоняется, а неправильный vhost не
пройдёт последующий route/egress/E2E. `allowInsecure` никогда не используется.

После будущей замены закреплённого leaf сохранённый pin перестанет совпадать — это
ожидаемая fail-closed остановка, а не повод включать `allowInsecure`. Публичный
CA-сертификат может штатно обновляться при сохранении валидной цепочки и
hostname.


4. Настроить DNS
================

Для точного frontend-имени оставьте:

  Type:       A
  Content:    IPv4 подключения сайта из ISPmanager
  CDN/proxy:  выключен, только DNS

Требуется ровно одна A-запись. Для этого же имени удалите AAAA и CNAME. Мастер
проверяет DNS A и введённый client-connect IPv4 независимо: он не выводит один
адрес из другого и не требует их равенства. DNS lookup всегда выполняется
локально на ПК/WSL, даже если frontend-доступ направлен через мост.

Не вводите вместо этого адрес FTP/SFTP-узла или IP exit. В схеме есть разные
адреса:

  - IPv4 подключения клиента к сайту;
  - hostname SFTP, получаемый из URL панели;
  - зарубежный IPv4 exit;
  - исходящий IPv4 Apache REG.RU, который мастер измерит автоматически.


5. Проверить учётную запись и SFTP
==================================

Режим `pc` принимает:

  - точный URL панели вида https://vipNNN.hosting.reg.ru:1500/;
  - основной логин REG.RU;
  - пароль панели.

Из hostname панели мастер выводит SFTP host, использует порт 22 и основной
логин. Поле «IP-адрес сервера» не является SFTP hostname. FTP- и MySQL-данные не
нужны для начального ввода.

Сначала пароль панели проверяется как SFTP-пароль основного аккаунта. Только при
точном SSH/SFTP authentication failure мастер скрыто спросит отдельный
SFTP-пароль. В письме REG.RU он подписан в разделе «Доступ к FTP»; вводите его
только в появившийся отдельный prompt. MySQL login/password/host не используются
никогда. Если credential принят, но document root недоступен, нужен разбор прав
аккаунта, а не перебор паролей. Всего допускается не более трёх попыток
SFTP-аутентификации: пароль панели и до двух вводов отдельного пароля.

Отдельные `ls/get/put/rename` не создают новый password-login каждый раз.
Мастер держит один приватный SFTP ControlMaster на ограниченную транзакцию:
document-root lookup, отдельный `302`-контроль `.htaccess`, каждую из трёх
последовательных `[P]`-проб и финальный apply/E2E/rollback. Это ограничивает
частоту входов, но не обходит лимиты
хостинга и не превращает сетевой timeout в повод повторять пароль.
Сомнительная write-команда не повторяется автоматически. Только чистая
транспортная ошибка rollback допускает один новый pinned-сеанс для сверки
существующего журнала. Конфликт чужих файлов, смешанная ошибка или неудачная
сверка оставляют rollback incomplete и блокируют продолжение.

Первый SFTP host key принимается автоматически по TOFU и сохраняется для
hostname:22. На первом контакте используется `ssh-keyscan`. На повторном запуске
мастер безопасно проверяет сохранённую приватную запись без нового scan, затем
немедленно открывает SFTP с `StrictHostKeyChecking=yes`. При исчезновении или
изменении ключа это реальное соединение блокируется до аутентификации и любых
изменений сайта.
TOFU не подтверждает личность узла через независимый канал при самом первом
контакте; для строгой модели угроз используйте ручной advanced runbook.

Если вывод говорит `SFTP SSH-транспорт не установился`, это transport/route
failure. При мосте хвост `Connection to UNKNOWN port 65535 timed out` относится
к stdio ProxyCommand; мастер всё равно нацелен на hostname панели по TCP/22.
Не открывайте 65535, не подставляйте FTP-IP и не удаляйте закреплённый ключ.
После cooldown хостинга допустим один повтор (15–30 минут — лишь осторожная
эвристика, если точное окно неизвестно). Второй такой же timeout означает STOP:
нужно проверить SFTP-host:22, rate-limit/ban и исходящий TCP/22 моста у
провайдера, а не запускать мастер циклом.


6. Прямой доступ или необязательный мост
========================================

После скрытого SSH password exit текущий PC-мастер спрашивает точно:

  Использовать мост для входа? [y/N]

Пустой Enter или `n/no/нет` означает прямой доступ к REG.RU. Если нужен мост,
введите `y`, `yes` или `да`. Сразу после него обязаны появиться IPv4 моста, SSH
login `[root]` и скрытый password; порт не спрашивается и равен 22. Если мастер
сразу перешёл к URL панели, остановите окно: мост не выбран либо запущена
другая/старая распакованная копия. Мастер принимает ключ моста по TOFU и требует
успешный вход с UID 0. Перед ISPmanager/SFTP/TLS он печатает `SSH-мост готов;
frontend control-plane направлен через него`; без этой строки не считайте мост
применённым.

Через мост во время setup идут HTTPS ISPmanager, SFTP и его first-use keyscan, TLS/SNI
frontend, HTTPS-запросы временной пробы и финальный E2E. SSH к exit остаётся
прямым, DNS проверяется локально. Мост не входит в Xray/datapath или клиентскую
ссылку и закрывается после setup. На нём ничего не устанавливается.

Прямые exit-команды группируются в ограниченные pinned SSH-сеансы, поэтому
проверки systemd, пакетов и портов не создают быстрый цикл password-login.
После firewall-мутации мастер отдельно проверяет новый независимый root-вход,
сохраняя прежний сеанс для разрешённого rollback. Потерянная команда не
повторяется автоматически, а transport failure не вызывает перебор паролей.

Fresh-подготовка exit допускает в active UFW только exact SSH guard текущего
порта. Resume допускает этот guard и полную exact managed-пару backend из
сохранённого состояния. Любое чужое, дублированное, частичное или wrong-port
user rule останавливает процесс. Второй мастер или параллельные ручные изменения
firewall запрещены; ранее изменённые raw UFW `before/after`/internal chains
требуют отдельного ручного аудита либо чистого VPS.

`exact_recovery=failed`, `exact_reconciliation=required` после неудачной
recovery-сессии и `rollback неполон` означают немедленный STOP. Не повторяйте
мастер до ручной сверки phase marker, exact UFW comments и указанного временного
каталога. Повтор допустим после `exact_recovery=succeeded` либо доказанного
read-only сбоя без мутации.

Эта optional-ветка текущего исходного кода подтверждена локальными/mocked-
тестами и реальным setup-доступом через мост к ISPmanager, SFTP и TLS/SNI.
Reverse-proxy проба проверенного узла не дошла до exit, поэтому успешного
полного live bridge E2E текущей версии всё ещё нет.


7. Что мастер изменит на сайте
==============================

Во время измерения Apache egress мастер временно добавляет только свой
маркированный блок `.htaccess`, делает несколько независимых запросов и
возвращает исходные bytes. Финальный apply так же транзакционно добавляет только
managed-блок XHTTP proxy.

Существующие строки `.htaccess` сохраняются. Перед переключением мастер повторно
сверяет исходный файл и не перезаписывает конкурентную чужую правку. При ошибке
E2E выполняется rollback; при неполном rollback дальнейший автоматический запуск
блокируется до ручной сверки backups.

`index.html`, `index.php` и остальное содержимое сайта не меняются. Режим
`placeholder_mode=keep` не создаёт нейтральную страницу, копию RuFox или
reverse proxy главной страницы.


8. Reverse-proxy capability и внешний firewall
===============================================

Мастер измеряет Apache egress по фактическим SYN на exit. При неудачной или
неоднозначной capture он добавляет безопасную сводку HTTP-результатов; эти два
сигнала нужно рассматривать вместе:

  - если все запросы дали HTTP 404, SYN нет, а диагностическое контрольное
    правило в том же XHTTP namespace с локальным redirect 302 срабатывает, это
    сильный контроль обработки Apache/.htaccess, но `[P]`/mod_proxy_http на
    узле/тарифе остаётся неподтверждённым; это не повод автоматически обвинять
    cloud firewall;
  - HTTP 5xx без SYN требует проверки error log Apache и поддержки
    mod_proxy/mod_proxy_http у провайдера;
  - transport timeout/connection error без SYN может означать маршрут либо
    provider cloud firewall exit.

Обычному пользователю не нужно вручную создавать контрольное правило: мастер
сам применяет его как отдельную кратковременную транзакцию с обязательным
rollback перед `[P]`-пробами. Не передавайте поддержке секретный XHTTP path,
UUID, пароли или VLESS URI; достаточно status histogram, результата
302-контроля и факта «zero SYN».

Если именно внешний firewall VPS блокирует transport probe, мастер напечатает
три точных случайных высоких TCP-порта. Временно разрешите входящий TCP только
на эти три значения и один раз повторите запуск с теми же данными — мастер
использует сохранённую тройку. После успешного измерения он напечатает Apache
egress `/32` и остановится на checkpoint. Пока окно ждёт Enter:

  1. закройте все три временных probe-порта;
  2. разрешите TCP/8083 только от напечатанного `/32`;
  3. вернитесь в то же окно и нажмите Enter.

Если отдельного cloud firewall/security group у VPS нет, ничего не открывайте и
на checkpoint просто нажмите Enter. UFW внутри exit мастер настраивает сам.


9. Готовность перед START-WINDOWS.cmd
=====================================

  [ ] Получено разрешение хостинга на такой трафик.
  [ ] Сайт вручную создан в ISPmanager.
  [ ] PHP -> FastCGI (Apache) включён.
  [ ] Провайдер подтвердил mod_rewrite, mod_proxy, mod_proxy_http и [P].
  [ ] TLS-vhost точного домена работает на 443.
  [ ] HSTS и HTTP -> HTTPS redirect выключены.
  [ ] Журнал запросов выключен; журнал ошибок включён.
  [ ] Сжатие и кеширование выключены.
  [ ] CGI, Python и ProxyRequests не включались.
  [ ] Для домена есть ровно одна A-запись; client-connect IPv4 известен отдельно.
  [ ] CDN/proxy выключен; AAAA и CNAME отсутствуют.
  [ ] Известны URL панели, основной логин/пароль, IPv4 подключения и домен.
  [ ] Основной аккаунт имеет SFTP-доступ к document root.
  [ ] Если нужен мост: известны его IPv4, UID-0 login/password; TCP/22 и
      forwarding доступны.
