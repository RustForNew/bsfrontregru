# Проверка развёртываний — 2026-08-19 и 2026-08-20

Документ фиксирует технические факты исходного предоставленного примера,
отдельного успешного чистого развёртывания и более поздней отрицательной live-
проверки текущего PC-мастера. Адреса, учётные данные, UUID, XHTTP path, VLESS
URI и ключевой материал не записываются.

Целевой контракт задаёт владелец: frontend REG.RU, TLS на клиентском плече,
VLESS Encryption, bare Xray exit без Remnawave. `METHOD-bs-front.md` и видео
использовались как источники для проверки, а не как исполняемые команды.

## Чистое развёртывание xhttp-setup

Подтверждено сквозной проверкой раздельных режимов `exit` и `front`:

- на exit установлен закреплённый Xray v26.3.27 с проверенным SHA-256;
- Xray работает отдельным непривилегированным systemd-пользователем, сервис
  включён, переживает restart и слушает только выбранный backend-порт;
- VLESS Encryption включён, транспорт — XHTTP `packet-up`, лимит POST явно
  согласован как 1 MB на сервере и клиенте;
- UFW разрешает backend только от одного измеренного Apache egress `/32`, затем
  запрещает порт остальным адресам; прямой тест с другого сервера отклонён;
- frontend — новый сайт REG.RU с `PHP → FastCGI (Apache)`. При выключенном PHP
  nginx отвечал 404 до обработки `.htaccess`; версия PHP не влияет на схему;
- SSL/443 привязан к нужному SNI-vhost. ISPmanager self-signed leaf закреплён по
  SHA-256 полного DER через `pinnedPeerCertSha256`/`pcs`; `allowInsecure` нет;
- password SFTP к hosting-node:22 прошёл с закреплённым host key и
  fail-on-command batch-семантикой. Первоначально отсутствующая `.htaccess`
  обработана как нормальное состояние, существующий index не изменён;
- временный Xray-клиент, сгенерированный установщиком, прошёл TLS/XHTTP
  через REG.RU и увидел ожидаемый IP exit. E2E повторно прошёл после restart
  exit и отдельных отрицательных проверок;
- неправильный leaf pin и неправильный VLESS UUID отклонены;
- поля URI сверены с JSON этого сгенерированного Xray-клиента: frontend
  IPv4:443, XHTTP, SNI/Host, `edge`, `pcs`, path, VLESS Encryption и `extra`
  совпадают. Это не проверка импорта GUI-клиентом;
- `client.vless` создан с правами `0600` только после успешного E2E.

## Отрицательная live-проверка release-candidate 0.6.1 — 2026-08-20

Эта проверка не заменяет и не отменяет успешный dataplane выше: использовался
другой shared-hosting узел. Она показывает, что одинаковые поля ISPmanager и
`FastCGI (Apache)` не гарантируют поддержку Apache reverse proxy на каждом
тарифе/узле.

- точный распакованный Windows artifact `0.6.1` был запущен через
  `START-WINDOWS.cmd`; ответ `y` выбрал мост, после чего появились его поля и
  мастер явно сообщил о готовности bridge;
- через мост успешно прошли read-only ISPmanager lookup, SFTP document-root и
  TLS/SNI frontend; значит, bridge был применён к этим setup-подключениям;
- ISPmanager подтвердил Apache/FastCGI, SSL/443, выключенные HSTS/redirect,
  access log/cache/gzip/CGI и включённый error log;
- SFTP-файл главной страницы совпал по размеру и SHA-256 с HTTP-ответом сайта:
  document root был выбран правильно, homepage не менялась;
- временное catch-all правило с локальным redirect `302` сработало; отдельное
  правило с точным сгенерированным XHTTP path и таким же `302` тоже сработало.
  Следовательно, запрос достиг нужного Apache, `.htaccess` и точного path;
- правило `RewriteRule ... [P,L]` для того же маршрута стабильно возвращало
  `404`, а capture на exit не увидел ни одного SYN. Отдельная прямая проверка
  показала, что SYN на временный порт exit в принципе достигает сервера;
- эти сигналы не подтверждают блокировку cloud firewall. На этом узле не была
  доказана необходимая capability/policy `mod_proxy` + `mod_proxy_http` + `[P]`.
  Точный внутренний механизм серверного `404` без доступа к конфигурации Apache
  не устанавливался;
- CGI и Python оставались выключенными. Их включение не требуется и не заменяет
  `mod_proxy_http`; `ProxyRequests On` также не нужен и не должен включаться;
- probe route был откатан. Xray/final frontend/client profile не применялись,
  успешного E2E текущего `0.6.1` через мост нет.

После cooldown 2026-08-21 был выполнен один ограниченный повтор для дальнейшей
диагностики. Мост снова открылся, но exit закрыл самый первый прямой SSH-сеанс
ещё на проверке доступа. Запуск остановился до ISPmanager, UFW, Xray и
`.htaccess`; локальная фаза осталась `preparing`, pending/handoff/firewall/client
артефакты не появились, transport-процессы и временные каталоги были очищены.
Повторы прекращены: точную внешнюю причину закрытия SSH без журналов VPS нельзя
честно отличить от лимита подключений, состояния sshd или сетевой политики.

Практический вывод: при сочетании «точный локальный `302` работает + все proxy-
запросы дают `404` + zero SYN» нужно остановиться и получить у провайдера
явное подтверждение `RewriteRule ... [P,L]` в пользовательском `.htaccess`.
Открытие probe-порта во внешнем firewall в такой ситуации само по себе не
подтверждает и не исправляет неподтверждённый reverse-proxy путь.

## Версии PC-мастера

Текущий публичный immutable Release — `v0.6.2`; его CI, Windows launcher и пять
артефактов проверены 2026-08-21. `v0.6.1` остаётся предыдущей версией: она
ошибочно отклоняет штатный пустой вывод UFW `(None)`. В `v0.6.2` этот marker
распознаётся как пустой inventory без ослабления отказа для смешанных или
неизвестных payload-строк.

Публикация `v0.6.2` не является новым успешным live E2E; исторические результаты
ниже относятся к указанным версиям.

## Исторический контракт публичного PC-мастера 0.6.0

Публичный Release `v0.6.0` автоматизирует тот же dataplane, не меняя проверенную
схему выше. Этот раздел фиксирует исторический реализованный контракт и
локальные/mocked-проверки того кода; публикация сама по себе не добавила новую
live-проверку к фактам развёртывания 2026-08-19.

- после exit IPv4/SSH port/login/password мастер точно спрашивает
  `Использовать мост для входа? [y/N]`; N/Enter оставляет прямой режим, а Y
  добавляет IPv4 моста, login `[root]` и скрытый пароль на фиксированном
  TCP/22;
- мастер принимает ключ моста по TOFU и требует фактический UID 0. Через мост
  во время setup идут ISPmanager HTTPS, SFTP/keyscan, frontend TLS, временная
  HTTPS-проба и финальный E2E; SSH к exit остаётся прямым, DNS lookup —
  локальным;
- мост является только setup control-plane: Xray там не устанавливается, адрес
  моста не входит в handoff/client URI и после настройки не участвует в
  datapath;
- после выбора прямого доступа или моста пользователь вводит точный URL
  ISPmanager, основной логин/пароль REG.RU, IPv4 подключения сайта и домен;
- сайт уже существует: ISPmanager используется read-only для единственного
  точного совпадения и фактического document root; create/edit через
  ISPmanager API отсутствуют;
- SSH/SFTP используют endpoint-scoped TOFU. Первый увиденный ключ сохраняется,
  последующее исчезновение/изменение закреплённого ключа блокируется;
- public TLS проверяется через системный CA и hostname. При certificate-
  verification отказе требуются два одинаковых TLS handshakes, после чего exact
  DER SHA-256 сохраняется и проверяется; обычно это ISPmanager self-signed leaf,
  но pin-режим сам не проверяет CA/hostname/vhost; `allowInsecure` отсутствует;
- сайт, DNS, SFTP/docroot и TLS проверяются до первой мутации нового exit;
- поддерживается только чистый Debian 12+/Ubuntu 22.04+ exit без
  Docker/containerd/custom firewall. Pristine inactive UFW включается через
  SSH allow, временный systemd rollback guard и новые SSH-проверки до и после
  остановки timer/service; stale guard или единственная exact orphaned SSH rule
  следующего запуска согласуется до apt, дополнительные rules блокируют процесс;
- egress exit и Apache frontend измеряются автоматически. Временный
  `.htaccess` применяется через тот же compare-and-swap/rollback механизм, что
  и финальный frontend;
- финальный backend остаётся TCP/8083 с точным UFW allow `/32` и deny;
- UUID и XHTTP path создаются автоматически, homepage/index не меняются
  (`placeholder_mode=keep`);
- URI выдаётся только после SOCKS E2E и совпадения внешнего IP с egress exit;
- phase/pending/receipt state позволяет после прерванного exit apply повторить
  точное состояние с теми же UUID/path. Незавершённый frontend rollback
  блокирует автоматическое продолжение fail-closed.

Пароли не входят в persistent recovery state. Отдельный SFTP-пароль запрашивается
только после точной ошибки SFTP-аутентификации, а не после сетевой или файловой
ошибки; общий предел — три попытки аутентификации.

## Исходный предоставленный пример

В старом рабочем примере были подтверждены Apache `[P]`, XHTTP `packet-up`,
зависимость REG.RU от `FastCGI (Apache)`, различие сертификатов с SNI и без SNI,
а также возможность frontend → exit по HTTP.

Его эксплуатационные решения не являются состоянием нового развёртывания:

- Xray binary брался из Remnawave-контейнера и запускался root-процессом;
- использовалась prerelease-версия Xray;
- backend был открыт диапазону `/16`, а не измеренному `/32`;
- XHTTP server оставлял default 1 MB, пока клиент объявлял 2 MB;
- присутствовали BBR/fq/MTU probing/MSS 1280.

`xhttp-setup` не переносит эти решения: он устанавливает stable binary, запускает
его без root, согласует 1 MB на обеих сторонах и не меняет BBR/fq/MSS.

## TLS и адреса frontend

TLS без сертификата невозможен. В проверенной pin-схеме публичный сертификат не
выпускался, но Apache предъявлял выбранный ISPmanager self-signed leaf.

До привязки SSL к сайту порт 443 открывал default-vhost провайдера и другой
сертификат. Поэтому leaf pin снимается только после проверки правильного сайта с
тем же `client-connect-ip` и SNI. Pin без SNI, CA hash и SPKI не подходят.

Различаются три адреса:

- IPv4, к которому подключается клиент;
- DNS A frontend-домена;
- исходящий IPv4 Apache, который видит exit.

В чистом развёртывании адрес Apache подтверждён соединением на exit. Его нельзя
выводить из A-записи, FTP-письма или шаблона сети провайдера.

## Не подтверждено

- импорт готового URI конкретным GUI-клиентом и сохранение `pcs`/Encryption;
- работа белого списка целевого мобильного оператора именно на TCP 443;
- публичный CA/Let's Encrypt сценарий;
- длительная нагрузка и стабильность Apache egress `/32` во времени;
- применимость `PHP → FastCGI (Apache)` к другим тарифам и узлам REG.RU;
- автоматический PC-orchestrator и включение pristine UFW не участвовали в
  успешной live-проверке 2026-08-19; запуск `0.6.1` 2026-08-20 дошёл через их
  preflight/подготовку до frontend probe, но не до Xray/final E2E;
- реальный bridge `0.6.1` подтверждён только для ISPmanager/SFTP/TLS setup-
  сегментов. Probe не прошёл из-за неподтверждённой provider reverse-proxy
  capability, поэтому полный bridge dataplane/E2E и его длительная стабильность
  не подтверждены;
- recovery после реального power loss/kill в каждой phase; поведение проверено
  автоматическими тестами и структурой receipt/marker, но не аппаратным сбоем;
- Windows launcher проверен настоящим Windows PowerShell 5.1 и локальным WSL2;
  2026-08-20 точный распакованный artifact прошёл реальные интерактивные
  preflight-шаги до frontend probe, но не завершил E2E;
- persistence optional MSS-профиля после reboot.

Создание сайта и сертификата через ISPmanager не автоматизировано. Форма панели
зависит от версии и тарифа; мастер использует готовый vhost и получает точный
document root read-only. Актуальная подготовка сайта находится в
[`reg-ru-ispmanager-setup.txt`](reg-ru-ispmanager-setup.txt). Большой
[`reg-ru-pinned-tls.txt`](reg-ru-pinned-tls.txt) — архивный ручной runbook
v0.4.x для legacy/advanced-эксплуатации, а не инструкция текущего PC-мастера.

## Границы автоматизации

Проект не использует `allowInsecure`, не меняет чужие Docker/Xray/systemd
namespace, не копирует сторонний сайт и не выдаёт VLESS URI до E2E со сверкой
IP выхода. PC-мастер заменяет независимую первичную сверку fingerprint exit,
необязательного моста и SFTP на TOFU: это сохраняет обнаружение последующей
смены ключа, но не аутентифицирует первый контакт против активного MITM. Правила
хостинга и provider cloud firewall остаются внешними условиями.
