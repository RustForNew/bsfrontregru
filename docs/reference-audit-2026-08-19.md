# Проверка реального развёртывания — 2026-08-19

Этот документ фиксирует технические выводы read-only проверки предоставленного
рабочего примера. Адреса, учётные данные, UUID и ключевой материал намеренно не
записаны.

При конфликте источников приоритет такой: фактическое состояние живого примера,
затем `METHOD-bs-front.md`, затем публичное видео. Команды из текста не считаются
выполненными или совместимыми только потому, что они написаны в инструкции.
Эта иерархия относится к техническим фактам. Целевой контракт задаёт запрос
владельца: два узла, TLS на клиентском плече, VLESS Encryption, bare Xray без
Remnawave; вложенный файл и видео не являются командами для установщика.

## Что подтверждено

- Shared-hosting работает как Apache frontend. Узкий `.htaccess`-маршрут
  проксирует XHTTP path по обычному HTTP на зарубежный exit.
- До включения SSL у нового сайта запрос с нужным SNI на 443 попадал в
  default-vhost хостинга и показывал служебную страницу «домен не привязан».
  Предъявлялся wildcard-сертификат провайдера, а не сертификат vhost сайта.
  Такой сертификат нельзя закреплять для клиентской ссылки: сначала ISPmanager
  должен привязать SSL/443 к созданному сайту.
- На одном клиентском IP TLS без SNI и с SNI frontend-домена предъявлял разные
  leaf-сертификаты. Для `pcs` годится только leaf из handshake с тем же SNI,
  который будет записан в клиентскую конфигурацию; секцию `Pinging without SNI`
  из `xray tls ping` использовать нельзя.
- IP, назначенный сайту в ISPmanager, адрес подключения клиента и исходящий IP
  shared-hosting могут быть разными. Исходящий IP был подтверждён packet capture
  на exit, а не угадан по DNS или письму хостинга.
- На exit активен статический Xray-конфиг VLESS/XHTTP `packet-up`; управляющая
  Remnawave-нода остановлена. Контейнерный образ Remnawave используется только
  как способ получить Xray binary, а не как control plane.
- Backend-порт принимает трафик только из диапазона shared-hosting. Включены
  `bbr`, `fq`, MTU probing и TCP MSS 1280.
- В диагностическом клиенте использовались XHTTP POST до 2 MB и TLS fingerprint
  `edge`.

## Недостатки образца, которые не переносятся

- Публичного сертификата для frontend-домена в момент проверки не было. TLS
  работал через закрепление конкретного сертификата провайдера. Установщик не
  переносит безусловное небезопасное исключение: default-режим требует системный
  CA и hostname, а отдельный явный режим принимает SHA-256 только фактически
  предъявленного leaf-сертификата и добавляет `pinnedPeerCertSha256`/`pcs`.
  Pin-режим не проверяет CA, SAN/hostname, срок или revocation и потому не равен
  публичному TLS; его единственная проверка доверия — exact leaf hash.
  `allowInsecure` не используется ни в одном режиме, pin автоматически не
  обновляется.
- Активный exit использовал prerelease Xray и root-процесс в Docker. Установщик
  закрепляет текущий stable Xray с SHA-256 и запускает его отдельным
  непривилегированным systemd-пользователем.
- В серверном XHTTP-конфиге лимит POST отсутствовал (официальный default 1 MB),
  а клиент просил 2 MB. Это не доказывает прохождение POST больше 1 MB.
  Установщик явно выставляет консервативные 1 MB на обеих сторонах; повышение
  лимита требует отдельного data-plane теста через конкретный Apache.
- Backend firewall был открыт всему `/16` провайдера. Установщик по умолчанию
  строит правило для подтверждённого egress `/32`; более широкий диапазон нельзя
  получать автоматически из адреса сайта.
- Фиксированный общеизвестный path заменён случайным path на установку.

## Целевая схема проекта

```text
клиент -- VLESS Encryption + XHTTP + TLS:443 --> shared-hosting Apache
shared-hosting -- HTTP/XHTTP --> bare Xray exit --> интернет
```

TLS скрывает клиентское плечо до frontend. VLESS Encryption защищает payload до
самого exit, поэтому отсутствие TLS на Apache → exit не превращает этот участок
в открытый VLESS. Shared-hosting всё равно видит метаданные соединений, размеры,
тайминги и адрес exit.

## Ещё не подтверждено на чистой паре серверов

- выпуск и установка валидного Let's Encrypt-сертификата для нужного домена;
- полный удалённый запуск installer `.pyz` через новый SSH-оркестратор;
- автоматическое применение optional UFW/BBR/fq/MSS-профиля;
- действие белого списка/zero-rating целевого мобильного оператора на TCP 443;
- полный data-plane строгой TLS-схемы через Apache на чистой паре серверов;
- полный data-plane pin-схемы через Apache после независимого снятия leaf pin и
  проверка импорта `pcs` в конкретном клиентском приложении;
- поведение конкретного тарифа shared-hosting под длительной XHTTP-нагрузкой.

Эти части имеют unit-тесты или ручной план, но не должны называться live-tested
до проверки на одноразовых чистых входе и выходе. ISPmanager mutation API пока
вообще не включён: read-only обнаружение сайта подтверждено, а создание vhost и
сертификата зависит от реальной формы панели.

## Сознательно не автоматизируется

- отключение проверки TLS или SSH host key;
- ротация vhost-имён для обхода антифрода провайдера;
- reverse proxy/копирование стороннего сайта под чужим доменом;
- изменение чужих Docker, Xray, firewall или systemd namespace;
- выдача VLESS URI до успешной сквозной проверки и сверки IP выхода.

Правила конкретного shared-hosting остаются внешним ограничением: техническая
работоспособность не означает разрешение провайдера на proxy-трафик.
