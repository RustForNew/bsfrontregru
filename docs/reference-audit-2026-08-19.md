# Проверка развёртываний — 2026-08-19

Документ фиксирует технические факты двух проверок: исходного предоставленного
примера и отдельного чистого развёртывания `xhttp-setup`. Адреса, учётные данные,
UUID, XHTTP path, VLESS URI и ключевой материал не записываются.

Целевой контракт задаёт владелец: frontend REG.RU, TLS на клиентском плече,
VLESS Encryption, bare Xray exit без Remnawave. `METHOD-bs-front.md` и видео
использовались как источники для проверки, а не как исполняемые команды.

## Чистое развёртывание xhttp-setup

Подтверждено сквозной проверкой раздельных режимов `exit` и `front`:

- на exit установлен закреплённый Xray v26.3.27 с проверенным SHA-256;
- Xray работает отдельным непривилегированным systemd-пользователем, сервис
  включён, переживает restart и слушает только выбранный backend-порт;
- VLESS Encryption включён, транспорт — XHTTP `packet-up`, лимит POST явно
  согласован как 1 MB на сервере и клиенте;
- UFW разрешает backend только от одного измеренного Apache egress `/32`, затем
  запрещает порт остальным адресам; прямой тест с другого сервера отклонён;
- frontend — новый сайт REG.RU с `PHP → FastCGI (Apache)`. При выключенном PHP
  nginx отвечал 404 до обработки `.htaccess`; версия PHP не влияет на схему;
- SSL/443 привязан к нужному SNI-vhost. ISPmanager self-signed leaf закреплён по
  SHA-256 полного DER через `pinnedPeerCertSha256`/`pcs`; `allowInsecure` нет;
- password SFTP к hosting-node:22 прошёл с закреплённым host key и
  fail-on-command batch-семантикой. Первоначально отсутствующая `.htaccess`
  обработана как нормальное состояние, существующий index не изменён;
- временный Xray-клиент, сгенерированный установщиком, прошёл TLS/XHTTP
  через REG.RU и увидел ожидаемый IP exit. E2E повторно прошёл после restart
  exit и отдельных отрицательных проверок;
- неправильный leaf pin и неправильный VLESS UUID отклонены;
- поля URI сверены с JSON этого сгенерированного Xray-клиента: frontend
  IPv4:443, XHTTP, SNI/Host, `edge`, `pcs`, path, VLESS Encryption и `extra`
  совпадают. Это не проверка импорта GUI-клиентом;
- `client.vless` создан с правами `0600` только после успешного E2E.

## Исходный предоставленный пример

В старом рабочем примере были подтверждены Apache `[P]`, XHTTP `packet-up`,
зависимость REG.RU от `FastCGI (Apache)`, различие сертификатов с SNI и без SNI,
а также возможность frontend → exit по HTTP.

Его эксплуатационные решения не являются состоянием нового развёртывания:

- Xray binary брался из Remnawave-контейнера и запускался root-процессом;
- использовалась prerelease-версия Xray;
- backend был открыт диапазону `/16`, а не измеренному `/32`;
- XHTTP server оставлял default 1 MB, пока клиент объявлял 2 MB;
- присутствовали BBR/fq/MTU probing/MSS 1280.

`xhttp-setup` не переносит эти решения: он устанавливает stable binary, запускает
его без root, согласует 1 MB на обеих сторонах и не меняет BBR/fq/MSS.

## TLS и адреса frontend

TLS без сертификата невозможен. В проверенной pin-схеме публичный сертификат не
выпускался, но Apache предъявлял выбранный ISPmanager self-signed leaf.

До привязки SSL к сайту порт 443 открывал default-vhost провайдера и другой
сертификат. Поэтому leaf pin снимается только после проверки правильного сайта с
тем же `client-connect-ip` и SNI. Pin без SNI, CA hash и SPKI не подходят.

Различаются три адреса:

- IPv4, к которому подключается клиент;
- DNS A frontend-домена;
- исходящий IPv4 Apache, который видит exit.

В чистом развёртывании адрес Apache подтверждён соединением на exit. Его нельзя
выводить из A-записи, FTP-письма или шаблона сети провайдера.

## Не подтверждено

- импорт готового URI конкретным GUI-клиентом и сохранение `pcs`/Encryption;
- работа белого списка целевого мобильного оператора именно на TCP 443;
- публичный CA/Let's Encrypt сценарий;
- длительная нагрузка и стабильность Apache egress `/32` во времени;
- применимость `PHP → FastCGI (Apache)` к другим тарифам и узлам REG.RU;
- PC-orchestrator, remote UFW и bridge-транспорт не участвовали в live-проверке
  2026-08-19; отдельно подтверждены только используемые ими серверные
  `exit`/`front` и E2E-контракты;
- Windows launcher/package проверен только структурно; полноценный запуск через
  WSL2 на реальных узлах отдельно не выполнялся;
- persistence optional MSS-профиля после reboot.

Создание сайта и сертификата через ISPmanager не автоматизировано. Форма панели
зависит от версии и тарифа; мастер использует готовый vhost и точный document
root. Пошаговый порядок находится в
[`reg-ru-pinned-tls.txt`](reg-ru-pinned-tls.txt).

## Границы автоматизации

Проект не отключает TLS/SSH host-key проверку, не меняет чужие Docker/Xray/
systemd namespace, не копирует сторонний сайт и не выдаёт VLESS URI до E2E со
сверкой IP выхода. Правила и лимиты хостинга остаются внешним условием.
