REG.RU SHARED FRONTEND + XHTTP + TLS PIN
Пошаговая подготовка сайта и запуск xhttp-setup

Назначение
==========

Схема:

  клиент -- VLESS/XHTTP + TLS :443 --> Apache сайта на REG.RU
  Apache -- HTTP/XHTTP --> Xray на зарубежном exit --> интернет

TLS в этой схеме заканчивается на Apache. На shared-hosting не устанавливаются
Xray, Docker, RemnaNode или фоновые процессы. Для TLS не требуется менять
зарубежный exit. Домен exit в клиентской ссылке не используется: address — это
проверенный IPv4 frontend, а frontend-домен используется как SNI и XHTTP Host.

Режим pinned нужен, когда Apache отдаёт на 443 сертификат хостинга, который не
проходит обычную проверку для frontend-домена. Клиент закрепляет SHA-256 точно
этого leaf-сертификата через pcs. Это не безусловный allowInsecure: соединение
принимается только при точном совпадении сертификата. Но при exact match Xray
не проверяет CA, SAN/hostname, срок действия и отзыв сертификата. Pin не равен
обычной публичной TLS-проверке.

Важно: pin не создаёт HTTPS-vhost. Сначала ISPmanager должен направить порт 443
с нужным SNI на созданный сайт. Только после этого снимается fingerprint.


1. DNS frontend
===============

Создать отдельный поддомен, например:

  front.example.org

В DNS Cloudflare создать одну запись:

  Type: A
  Name: front
  Content: <IP shared-hosting, выданный для сайта>
  Proxy status: DNS only, серое облако
  TTL: Auto

На этом имени не должно быть одновременно AAAA или CNAME. Cloudflare proxy для
этой записи не включать.

Если личный кабинет REG.RU при «Подключении домена» пишет «Неверное имя
домена» для поддомена, не добавлять его через это окно. Поддомен создаётся как
отдельный сайт непосредственно в ISPmanager: Сайты -> Добавить сайт.

Отдельная A-запись вроде exit.example.org допустима для администрирования, но
данная XHTTP-схема её не использует. Сертификат для неё не нужен.


2. Создание сайта в ISPmanager
==============================

Открыть ISPmanager с российского IP, если хостинг ограничивает вход по стране.
Не перебирать пароли: несколько ошибочных попыток могут вызвать временную
блокировку.

Сайты -> Добавить сайт. Заполнить:

  Имя:                 полный FQDN, например front.example.org
  Псевдонимы:          пусто
  Корневая директория: предложенная ISPmanager директория этого FQDN
  Источник IP-адреса:  получить автоматически
  E-mail администратора: действующий адрес владельца
  Кодировка:           не указывать
  Индексная страница:  index.php index.html
  Редирект домена:     не включён
  Автоподдомены:       отключено

При первом создании сайта SSL можно оставить выключенным. Он включается
отдельно после того, как сайт появился в списке.

Снять галочки:

  HSTS
  Перенаправлять HTTP-запросы в HTTPS
  SSI
  CGI-скрипты
  Python
  Тестовый домен для WordPress
  php.ini для домена
  Журнал запросов
  Настроить сжатие
  Настроить кеширование

Оставить:

  PHP:                  включён
  Режим работы PHP:     FastCGI (Apache)
  Журнал ошибок:       включён
  Период ротации:      ежедневно
  Хранить архивов:     3
  Генератор отчётов:   отключён

На проверенной конфигурации REG.RU галочка PHP и режим FastCGI (Apache) нужны
не для исполнения PHP-кода, а чтобы nginx передавал отсутствующие пути в Apache,
где срабатывает `.htaccess`. При выключенном PHP запрос к XHTTP path завершается
nginx 404 до правил Apache. Версия PHP несущественна: схема не содержит и не
запускает PHP-файлы. Опцию «php.ini для домена» оставить выключенной.

Поле «Расширения файлов для кеширования» не менять: при выключенной галочке
«Настроить кеширование» оно не участвует в работе сайта.

Нажать «Создать».


3. Проверка IP и обычного HTTP-vhost
====================================

После создания открыть карточку сайта и посмотреть фактически назначенный ему
IP. Не считать автоматически, что IP сайта, FTP IP и исходящий IP Apache
совпадают: это три разные роли.

До дальнейшей настройки проверить, что запрос к нужному IPv4 с Host frontend-
домена открывает именно новый сайт, а не чужой/default-vhost:

  curl -sS --resolve front.example.org:80:<FRONT_IP> \
    http://front.example.org/ -o /tmp/front-http.html

Если открывается служебная страница другого сайта, остановиться. В ISPmanager
нужно выбрать правильный доступный IP для сайта; угадывать его по FTP-письму
нельзя.


4. Включение SSL у сайта без Let's Encrypt
===========================================

Открыть Сайты -> нужный сайт -> Изменить и задать:

  Защищённое соединение (SSL): включено
  SSL-порт:                    443
  SSL-сертификат:              сертификат, который ISPmanager назначил сайту
  HSTS:                        выключено
  HTTP -> HTTPS:               выключено на время проверки

Сохранить. Собственный Let's Encrypt для режима pinned не обязателен. Но TLS на
443 всё равно существует: Apache предъявляет сертификат, который мы закрепим в
клиенте.

Диагностически получить HTTPS-страницу с тем же SNI и тем же IPv4:

  curl -skS --resolve front.example.org:443:<FRONT_IP> \
    https://front.example.org/ -o /tmp/front-https.html

Ключ -k здесь разрешён только для этой локальной проверки содержимого до
снятия pin. В VLESS-клиенте allowInsecure не включается.

Сравнить HTTP и HTTPS страницы:

  sha256sum /tmp/front-http.html /tmp/front-https.html

Одинаковый хеш — простой признак, что 80 и 443 ведут на один vhost. Если по 443
видна страница «домен не привязан» или другой сайт, pin снимать нельзя: сначала
исправить SSL-привязку в ISPmanager.


5. Получение SHA-256 leaf-сертификата
=====================================

Снимать pin только после шага 4. На доверенной Linux-машине/WSL:

  openssl s_client -connect <FRONT_IP>:443 \
    -servername front.example.org </dev/null 2>/dev/null \
    | openssl x509 -outform DER \
    | sha256sum

Нужны первые 64 hex-символа результата. Это SHA-256 полного DER leaf-
сертификата, не fingerprint CA и не SPKI.

Параметр -servername обязателен. Один и тот же Apache может предъявлять разные
сертификаты с SNI и без SNI. Нельзя брать hash из секции «without SNI» команды
`xray tls ping`: VLESS-клиент отправляет SNI frontend-домена, поэтому закреплять
нужно сертификат именно этого SNI-vhost.

Получение pin с одного сетевого пути является TOFU, а не независимой проверкой
личности сервера. По возможности сверить результат из второй доверенной сети
или с данными провайдера. После несовпадения pin нельзя автоматически принимать
новый сертификат с того же непроверенного соединения.


6. Запуск xhttp-setup
====================

Для новой пары серверов сначала один раз выполняется режим «Только выход» на
зарубежном VPS. Это устанавливает bare Xray и создаёт защищённый handoff.json.
TLS pin к этому шагу отношения не имеет.

Если exit уже настроен и есть его актуальный handoff.json, повторно запускать
установку exit только ради TLS нельзя. Использовать существующий handoff.

Frontend-шаг запускать с российской Linux-машины/моста, с которого разрешён
SFTP-доступ к хостингу:

  python3 xhttp-setup-0.1.0.pyz wizard

Выбрать:

  3. Только frontend по готовому handoff.json

Ввести по запросам:

  путь к защищённому handoff.json;
  frontend FQDN;
  IPv4 подключения клиента;
  ожидаемый IPv4 DNS A;
  на вопрос о закреплении leaf-сертификата ответить «да»;
  SHA-256 из шага 5;
  SFTP host, порт 22 и пользователя;
  точный document root сайта;
  независимо проверенный SHA-256 host key SFTP;
  для первого запуска оставить существующий index.html.

Использовать SFTP, не обычный FTP. Пароль вводится интерактивно и не должен
попадать в командную строку, историю shell, README или GitHub.

Неинтерактивный эквивалент pin-параметров:

  --tls-mode pinned \
  --tls-cert-sha256 '<64 hex SHA-256 leaf>'

После применения мастер обязан выполнить E2E-тест. Он выдаёт VLESS URI только
если запрос реально прошёл через локальный Xray/SOCKS и внешний IP совпал с
ожидаемым IP exit.


7. Что должно оказаться в клиенте
=================================

В VLESS URI должны одновременно присутствовать:

  address=<FRONT_IP>
  port=443
  type=xhttp
  security=tls
  sni=front.example.org
  host=front.example.org
  fp=edge
  pcs=<64 hex SHA-256 leaf>
  mode=packet-up
  path=<случайный path из handoff>
  encryption=<значение VLESS Encryption из handoff>

В сгенерированном Xray JSON должно быть:

  streamSettings.security = "tls"
  tlsSettings.serverName = "front.example.org"
  tlsSettings.fingerprint = "edge"
  tlsSettings.pinnedPeerCertSha256 = "<64 hex SHA-256 leaf>"

Параметра allowInsecure быть не должно. SNI и XHTTP Host не заменяются IP.

Клиент должен поддерживать pcs/pinnedPeerCertSha256 и не выбрасывать этот
параметр при импорте. С неподходящим или self-signed сертификатом удаление pcs
обычно завершится ошибкой проверки. Если leaf одновременно валиден для домена
через публичный CA, возможен незаметный переход к обычной PKI-проверке без pin.
Поэтому после импорта обязательно проверить итоговый JSON профиля клиента.


8. Смена сертификата и финальные проверки
==========================================

Pin привязан к одному leaf-сертификату. При его замене/перевыпуске старые
клиенты перестанут подключаться. Правильный порядок восстановления:

  1. Убедиться, что 443 всё ещё ведёт на нужный vhost.
  2. Независимо проверить новый сертификат.
  3. Снять новый SHA-256.
  4. Повторно выпустить клиентскую ссылку.
  5. Заменить профиль у клиентов.

Нельзя лечить несовпадение включением allowInsecure.

После успешного E2E отдельно проверить подключение с той SIM/сети, ради которой
создаётся схема. Доступность сайта на 80 не доказывает, что конкретный белый
список пропускает TCP 443.

Backend-порт exit должен быть закрыт от всех адресов, кроме фактического
исходящего IP Apache. Этот IP определяется на exit по реальному запросу; его
нельзя брать из DNS A или FTP-письма без проверки.
