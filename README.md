# XHTTP Setup

Standalone-мастер для схемы:

```text
клиент -- VLESS Encryption + XHTTP packet-up + TLS :443 --> сайт frontend
Apache frontend -- HTTP/XHTTP --> зарубежный bare Xray exit :8083 --> интернет
```

На shared-hosting не устанавливаются Xray, Docker или фоновые сервисы. TLS
завершается на существующем сайте, а Xray работает отдельным
непривилегированным systemd-сервисом только на зарубежном exit.

## Быстрый запуск на Windows

1. Один раз установите WSL2 с Ubuntu или Debian. Для Ubuntu:

   ```powershell
   wsl --install -d Ubuntu
   ```

   Если Windows попросит перезагрузку, перезагрузитесь и один раз откройте
   Ubuntu. Дальше вручную ставить Linux-пакеты не нужно: launcher проверит и при
   необходимости установит их сам.

2. В ISPmanager заранее вручную создайте сайт и настройте DNS/TLS по
   [короткому списку](docs/reg-ru-ispmanager-setup.txt). Мастер сайт не создаёт.
3. Скачайте
   [`xhttp-setup-0.5.0-windows-wsl.zip`](https://github.com/RustForNew/bsfrontregru/releases/download/v0.5.0/xhttp-setup-0.5.0-windows-wsl.zip),
   выберите в Проводнике «Извлечь все» и дважды нажмите
   `START-WINDOWS.cmd`.
4. Отвечайте на вопросы по одному. Никакие SHA-256, host-key fingerprint,
   UUID, XHTTP path, egress-IP, UFW-команды или `APPLY PC` вводить не нужно.
5. Не закрывайте окно до сообщения об успешной сквозной проверке. Только после
   неё мастер создаст `client.vless` и покажет клиентскую ссылку.

Полная инструкция для скачанного Windows ZIP находится в
[`windows/INSTRUCTION.txt`](windows/INSTRUCTION.txt). В release она публикуется
как самостоятельный файл с подставленной версией.

## Что нужно ввести

Обычный PC-мастер задаёт ровно семь видимых и два скрытых вопроса:

1. IPv4 выходного сервера;
2. SSH port выхода, обычно `22`;
3. SSH login выхода, нужен прямой `root`;
4. SSH password выхода — скрытый ввод;
5. точный HTTPS-адрес панели REG.RU/ISPmanager, включая порт, например
   `https://vip123.hosting.reg.ru:1500/`;
6. основной логин REG.RU;
7. пароль панели REG.RU — скрытый ввод;
8. IPv4 подключения REG.RU из карточки/данных подключения сайта;
9. домен frontend.

Пароль панели сначала проверяется для SFTP основного аккаунта. Только если SFTP
вернул именно ошибку аутентификации, мастер дополнительно и скрыто спросит
отдельный SFTP-пароль; всего допускается не более трёх попыток. При сетевой
ошибке, неверном document root или другой ошибке он не перебирает пароли.

## Что версия 0.5.0 делает автоматически

- принимает первый SSH-ключ exit и SFTP-ключ frontend по TOFU, сохраняет их для
  конкретного endpoint и останавливается при последующей смене ключа;
- проверяет root SSH и существующий сайт read-only запросом ISPmanager; сайт и
  его настройки через API не создаёт и не меняет;
- проверяет ровно одну A-запись домена, отсутствие AAAA, точные SNI и IPv4
  подключения;
- использует обычную проверку публичного CA, а при её отказе автоматически
  закрепляет SHA-256 стабильного точного leaf-сертификата (обычно self-signed);
  `allowInsecure` не создаётся;
- сначала проверяет сайт, DNS, SFTP и TLS без изменений на exit;
- готовит чистый Debian 12+/Ubuntu 22.04+ exit: ставит только разрешённый набор
  пакетов, безопасно подготавливает UFW и сохраняет SSH-доступ;
- измеряет фактические egress IPv4 exit и Apache REG.RU, выбирает стабильный
  для endpoint свободный probe-порт, создаёт UUID и случайный XHTTP path;
- применяет на exit точную пару UFW: allow backend только от измеренного
  frontend IPv4 `/32`, затем deny для остальных;
- транзакционно добавляет только managed-блок `.htaccess`, не перезаписывая
  чужие правила и не трогая главную страницу сайта;
- запускает временный локальный Xray-клиент, проверяет SOCKS-трафик через
  frontend и требует совпадения внешнего IP с egress-IP exit;
- выдаёт VLESS URI только после успешного E2E.

Мастер не создаёт сайт, не выпускает домен, не настраивает DNS-провайдера и не
копирует, не маскирует и не reverse-proxy'ит RuFox или любой другой сайт.
`index.html` и содержимое главной страницы остаются без изменений
(`placeholder_mode=keep`).

## Требования перед запуском

### Существующий frontend

- сайт уже создан вручную в ISPmanager;
- домен имеет ровно одну A-запись, без AAAA/CNAME для этого имени и без
  CDN/proxy; DNS A и введённый client-connect IPv4 проверяются как разные роли;
- TLS-vhost сайта работает на 443;
- HSTS и принудительный HTTP → HTTPS redirect выключены на время настройки;
- PHP работает в режиме `FastCGI (Apache)`, чтобы запрос неизвестного XHTTP path
  доходил до Apache и `.htaccess`;
- основной аккаунт имеет SFTP-доступ к фактическому document root сайта;
- Apache разрешает `mod_rewrite`, `mod_proxy`, `mod_proxy_http` и флаг `[P]`.

Мастер сам получает точный document root из уже существующей записи сайта в
ISPmanager. Совпадение домена должно быть единственным; неоднозначный ответ
панели отклоняется.

### Чистый exit

- Debian 12+ или Ubuntu 22.04+ с systemd;
- стабильный публичный IPv4 и прямой root SSH по паролю;
- свободный TCP/8083;
- нет Docker/containerd, чужого Xray, отдельного активного/enabled
  `nftables.service`, custom nftables/iptables и нестандартной сохранённой
  конфигурации UFW.

Активный поддерживаемый UFW сохраняется. Если UFW ещё не активен, мастер
автоматически создаёт SSH allow, включает временный systemd rollback guard,
включает UFW и подтверждает вход новой SSH-сессией. При неоднозначном состоянии
он останавливается, а не пытается объединить чужой firewall.

Провайдерский cloud firewall/security group находится вне VPS и не управляется
по SSH. Обычная установка не требует открывать диапазон портов. Если этот слой
блокирует probe, мастер показывает точный стабильный высокий TCP-порт:
временно разрешите только его и повторите запуск с теми же данными. После
измерения закройте probe-порт и разрешите TCP/8083 только от напечатанного IP
REG.RU `/32`. Без API конкретного провайдера полностью автоматизировать этот
слой невозможно.

## TOFU: точный компромисс

Ручной SHA/fingerprint больше не нужен. При первом соединении мастер принимает
увиденный SSH/SFTP-ключ и сохраняет точную запись; при следующих запусках
исчезновение или смена закреплённого ключа блокирует подключение.

Это сохраняет шифрование и защиту от незаметной подмены **после первого
успешного контакта**, но не подтверждает первый ключ через независимый канал.
Активная MITM-атака именно при первом запуске может закрепить чужой ключ. Если
такая модель угроз важна, независимо сверьте fingerprint у провайдера и
используйте расширенный ручной режим. Доверие пользователя своему персональному
компьютеру этого риска в сети не устраняет.

Для leaf, не прошедшего публичную CA+hostname проверку, действует аналогичный
first-contact pin: мастер выполняет две независимые TLS-сессии, требует
одинаковый DER, сохраняет его SHA-256 и блокирует смену leaf. В этом режиме
срок, CA и hostname уже не проверяются; exact pin не доказывает сам по себе
правильность Apache vhost. Переход на сертификат публичного CA допускается
только после обычной проверки системным trust store и hostname; публичный
сертификат может штатно обновляться.

## Повторный запуск и восстановление

Состояние PC-установки хранится отдельно для домена с закрытыми правами. Пароли
в него не записываются. Фазы `preparing`, `exit_applying`, `exit_ready` и
`complete` позволяют после сбоя проверить существующий managed exit и безопасно
продолжить с теми же UUID и XHTTP path. Изменившийся egress-IP не принимается
автоматически.

Во время временного probe и финального frontend apply мастер использует
транзакцию и rollback. Если процесс был жёстко прерван в фазе
`front_probe_in_progress` или `front_in_progress`, следующий запуск
останавливается fail-closed: сначала нужно сопоставить сохранённые backups с
текущим `.htaccess`. Не удаляйте каталог состояния и не запускайте второй
экземпляр параллельно.

Если frontend/E2E не завершён, exit может уже быть установлен и защищён UFW, но
`client.vless` не выдаётся.

## Запуск на Linux

Поддерживаемый контроллер — Debian 12+/Ubuntu 22.04+ с Python 3.10+. Скачайте
`.pyz` и `.pyz.sha256` одного release, проверьте checksum и запустите:

```bash
(
  set -Eeuo pipefail
  HASH="$(tr -d '\r\n' < xhttp-setup-0.5.0.pyz.sha256)"
  test "${#HASH}" -eq 64
  printf '%s  xhttp-setup-0.5.0.pyz\n' "$HASH" | sha256sum -c -
  python3 xhttp-setup-0.5.0.pyz --version
  exec python3 xhttp-setup-0.5.0.pyz pc
)
```

Из исходников:

```bash
python3 -m xhttp_setup pc
```

## Расширенные режимы

`pc` — основной и единственный минимальный сценарий для обычного пользователя.
Команды `exit`, `front`, `full` и `doctor` сохранены для диагностики,
раздельного применения и ручной эксплуатации. Они намеренно могут требовать
handoff, fingerprint, firewall acknowledgement и точное подтверждение apply.
Не переносите их вопросы в PC-инструкцию.

Архивный проверенный ручной runbook v0.4.x сохранён в
[`docs/reg-ru-pinned-tls.txt`](docs/reg-ru-pinned-tls.txt). Он описывает другой
workflow и не должен смешиваться с автоматическим мастером v0.5.0.

## Безопасность изменений frontend

Frontend меняется через SFTP-транзакцию:

- чужие строки `.htaccess` сохраняются, меняется только managed-блок;
- непосредственно перед переключением повторно сверяется исходный файл;
- при E2E-ошибке свои изменения откатываются к pre-apply снимкам;
- конкурентная чужая правка не перезаписывается;
- backups имеют случайные имена, локальные каталоги и секретные артефакты —
  закрытые права;
- `index.html` и остальные файлы сайта не меняются.

Подробная модель угроз и восстановление описаны в [`SECURITY.md`](SECURITY.md).

## Файлы на exit и локальном компьютере

```text
/opt/xhttp-setup/xray/v26.3.27/       закреплённый Xray и manifest
/etc/xhttp-setup/xray.json            managed-конфиг, 0640
/etc/systemd/system/xhttp-setup-xray.service
/var/lib/xhttp-setup/handoff.json     клиентский материал, 0600
/var/lib/xhttp-setup/firewall-plan.txt
/var/lib/xhttp-setup/current.json     receipt применённого состояния
~/.local/state/xhttp-setup/           TOFU и PC recovery state
```

Не публикуйте `handoff.json`, `client.vless`, recovery state или VLESS URI.

## Ограничения

- один frontend-домен, ровно одна A-запись и отсутствие AAAA;
- один стабильный frontend egress IPv4 `/32`;
- bare Xray exit; существующие Docker/Remnawave/custom firewall не мигрируются;
- мастер не управляет DNS, ISPmanager site creation и provider cloud firewall;
- публичный CA и стабильный exact-pinned leaf поддерживаются, произвольная смена
  закреплённого сертификата требует явного восстановления доверия;
- импорт итоговой ссылки конкретным GUI-клиентом остаётся отдельной проверкой.

## Правила REG.RU

Справка REG.RU продолжает перечислять proxy-сервисы среди запрещённого контента
на виртуальном хостинге. Техническая работоспособность схемы не даёт разрешения
провайдера и не гарантирует отсутствие блокировки. Используйте её только после
письменного разрешения REG.RU либо на хостинге, где такой трафик явно разрешён:

https://help.reg.ru/support/hosting/zakaz-hostinga-rabota-s-uslugoy/sovety-po-vyboru-tarifa-hostinga

Мастер не обходит антифрод, лимиты или блокировки, не ротирует домены и не
маскирует трафик под сторонний сайт.
